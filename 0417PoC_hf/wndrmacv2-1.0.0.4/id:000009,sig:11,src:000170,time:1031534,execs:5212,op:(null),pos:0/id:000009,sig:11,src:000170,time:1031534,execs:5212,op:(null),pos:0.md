# 漏洞分析: wndrmacv2-1.0.0.4 / id:000009,sig:11,src:000170,time:1031534,execs:5212,op:(null),pos:0

## 摘要

- 判定: `确认漏洞`
- Sink位置: `/usr/sbin/uhttpd do_asp@0x004119d8 0x00411a20 (jalr -> sym.imp.sprintf)`
- Source位置: `/usr/sbin/uhttpd handle_request@0x0040afd4 0x0040b024 (fgets 读入请求行，后续经 strsep/局部变量传递 URI)`
- 漏洞二进制: `/usr/sbin/uhttpd`
- 漏洞类型: `栈缓冲区溢出 / 返回地址覆盖`
- 一句话根因: `do_asp` 把攻击者可控 URI 用 `sprintf(sp+0x18, "/www/%s", uri)` 写入栈缓冲区且无长度检查，超长路径覆盖保存的返回地址，函数返回时跳到 `0x61616160` 崩溃。
- 数据包字段 -> 变量赋值:
  - `request.prefix` + `request.handler_name` -> HTTP request-line 中的 URI token -> `handle_request` 栈变量 `[sp+0x2730]` / 寄存器 `s3` -> `do_asp` 的 `a0`
  - `request.method=GET` -> `handle_request` 中的方法分支检查 -> 允许进入页面处理/回调分发逻辑
  - `request.handler_name` 中的 `.htm/.html` 形态内容 -> `handle_request` 对 `obj.mime_handlers` 的 `strstr(uri, handler_pattern)` 匹配 -> 命中 `do_asp` 回调
- 执行顺序:
  1. `handle_request` 从 socket 读入请求行，并把 URI token 保存在局部变量 `[sp+0x2730]`。
  2. `handle_request` 在 `obj.mime_handlers` 中匹配 URI，选中回调 `do_asp`，以 `a0=s3(uri)`、`a1=s2(FILE*)` 调用之。
  3. `do_asp` 在 `0x00411a20` 执行 `sprintf(sp+0x18, "/www/%s", uri)`，超长 URI 覆盖返回地址；随后即使 `fopen` 失败，函数返回时仍因返回地址被污染而在 `0x00411d48` 附近跳向 `0x61616160` 并触发 `SIGSEGV`。

## 数据流细节

- 哪些数据包字段控制了哪些变量:
  - `request.method` 控制 `handle_request` 的方法分支。
  - `request.prefix="/"` 与超长 `request.handler_name` 一起组成 URI，进入 `handle_request` 的请求行缓冲区。
  - 该 URI token 经过 `strsep`/局部变量传递，最终在 `handle_request` 中以 `[sp+0x2730]`、寄存器 `s3` 的形式保存，并在 `0x0040c3f8` 作为 `do_asp` 的 `a0` 传入。
- 哪个函数读取了source字段:
  - `handle_request` 在 `0x0040b024` 通过 `fgets(sp+0x20, 0x2710, s2)` 读入整条 HTTP request-line。
  - 后续 `strsep` 调用把请求行切分为 method/URI/version，URI 指针落入局部变量槽位并最终被装入 `s3`。
- 哪个函数写入 / 拼接 / 格式化了攻击者可控数据:
  - `do_asp` 在 `0x00411a20` 调用 `sprintf`，格式串为 `"/www/%s"`，目标缓冲区是当前栈帧中的 `sp+0x18`。
  - `do_asp` 栈帧大小为 `0x4c8`，保存的返回地址位于 `sp+0x4c4`；因此格式化结果只要超过 `0x4ac` 字节即可覆盖返回地址。
  - 本次 `request.handler_name` 长度为 `7493` 字节，远超覆盖阈值；即使只考虑 `"/www/" + uri + "\\0"`，也会大量越界写。
- 最终如何到达sink:
  - `handle_request` 在 `obj.mime_handlers` 循环中执行 `strstr(uri, handler_pattern)`，并在命中后取 `s4+0x10` 作为回调。
  - trace 已证明该回调实际为 `do_asp`，随后立即进入 `do_asp` 并执行危险的 `sprintf`。
  - `fopen` 是否成功不影响漏洞成立，因为溢出在文件存在性检查之前已经发生。

## 误报检查

- 为什么这是一个真实漏洞，或者为什么它更像误报:
  - 崩溃并非单纯因为访问了不存在页面。trace 显示控制流进入 `do_asp` 后，仅执行了 `sprintf`、`fopen`，随后就在返回尾声崩溃；而 `sprintf` 是发生在 `fopen` 之前的无界栈写。
  - `si_addr=0x61616160` 明显来自攻击者填充的 `'a'` 模式，符合返回地址/控制流被覆盖后的跳转目标，而不是普通空指针或文件打开失败。
  - 栈布局与输入长度可以静态证明越界范围足以覆盖保存的返回地址，因此这是可解释、可复现的数据流到控制流破坏。
- 当前缺失的证据:
  - 没有运行时寄存器转储去直接展示 `ra` 的最终值。
  - 没有精确还原 `obj.mime_handlers` 中本次命中的具体 pattern 字符串名称。
  - 这些不影响漏洞确认，因为 trace 已证明回调确实进入 `do_asp`，而 sink 及越界条件已被静态核实。
- 对当前现象的替代解释:
  - 最合理的替代解释是“文件不存在导致 `fopen` 失败后正常返回”；但这无法解释 `si_addr=0x61616160`，也无法解释为何在返回尾声发生控制流异常。
  - 因此“普通 404/文件缺失”不是更合理解释。
