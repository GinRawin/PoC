# 漏洞分析: wndrmacv2-1.0.0.4 / id:000016,sig:11,src:000316,time:4065080,execs:16928,op:(null),pos:0

## 摘要

- 判定: `确认漏洞`
- Sink位置: `/usr/sbin/uhttpd sym.do_file 0x4089cc`
- Source位置: `/usr/sbin/uhttpd sym.handle_request 0x40b048-0x40b050 / 0x40c3f8`
- 漏洞二进制: `debug/fs/usr/sbin/uhttpd`
- 漏洞类型: `栈缓冲区溢出 / 返回地址覆盖`
- 一句话根因: `handle_request` 将请求行中的 URI token 直接传给 `do_file`，`do_file` 在 `0x4089cc` 用 `sprintf(sp+0x18, "/www/%s", uri)` 写入固定 0xa8 字节栈帧，超长 URI 覆盖了 `sp+0xa0` 处保存的 `ra`，函数返回时崩溃。
- 数据包字段 -> 变量赋值:
  - `request.handler_name` -> 请求行中的 URI 主体内容 -> `handle_request` 栈变量 `*(sp+0x2730)` -> `s3` -> `do_file(a0)`
  - `request.method = GET` -> `fp` 指向的第一个 token，经 `strcasecmp(fp, "get")` 命中 GET 分支
  - `request.handler_name` 末尾 `.css` -> 在 `handle_request` 的 MIME/扩展名匹配逻辑中命中静态文件处理回调，最终落到 `do_file`
- 执行顺序:
  1. `uhttpd` 在 `handle_request` 中用 `fgets` 读取 HTTP 首行到 `sp+0x20`，再用 `strsep` 解析出方法与 URI，URI 指针保存在 `sp+0x2730`。
  2. GET 请求进入静态文件/MIME 处理路径，`0x40c3f8` 将 `s3 = *(sp+0x2730)` 作为 `a0` 传给 `do_file`。
  3. `do_file` 在 `0x4089cc` 执行 `sprintf(sp+0x18, "/www/%s", a0)`，超长 URI 覆盖保存的返回地址；`0x408a94` 取回被污染的 `ra` 后触发 `SIGSEGV`。

## 数据流细节

- 哪些数据包字段控制了哪些变量:
  - `request.handler_name` 提供了超长 `.css` 路径内容。结合 `handle_request` 的请求行解析和静态文件分发逻辑，可将其对应到第二个请求行 token（URI），即 `*(sp+0x2730)`。
  - `request.method = GET` 控制 `handle_request` 走 GET 分支，而不是 POST/SOAP 分支。
  - `.css` 后缀控制 MIME/静态文件分派，使 `s4->0x10` 指向的处理函数非空并在 `0x40c3fc` 被调用；该回调即 `do_file`。
- 哪个函数读取了source字段:
  - `sym.handle_request` 在 `0x40b010-0x40b028` 用 `fgets` 读取请求首行到 `sp+0x20`，随后在 `0x40b048-0x40b050` 与 `0x40b098-0x40b0a4` 用 `strsep` 解析空格分隔的 token。
  - 第一次 `strsep` 取出方法，第二次 `strsep` 取出 URI；URI 指针保留在 `sp+0x2730`，后续在 `0x40c3b8` 读入 `s3`。
- 哪个函数写入 / 拼接 / 格式化了攻击者可控数据:
  - `sym.do_file` 在 `0x4089c4-0x4089d0` 设置参数，`0x4089cc` 调用 `sprintf`，目的缓冲区为 `sp+0x18`，格式串为 `"/www/%s"`，源参数为攻击者可控 URI。
- 最终如何到达sink:
  - `request.handler_name` -> 请求行 URI token -> `handle_request` 的 `*(sp+0x2730)` -> `s3` -> `0x40c3f8 move a0, s3` -> `do_file(a0, s2)` -> `0x4089cc sprintf(sp+0x18, "/www/%s", a0)` -> 覆盖 `sp+0xa0` 保存的 `ra` -> `0x408a94` 崩溃。

## 误报检查

- 为什么这是一个真实漏洞，或者为什么它更像误报:
  - 崩溃点在 `do_file` 尾部 `lw ra, [sp+0xa0]`，不是空指针随机崩溃，而是典型的返回地址破坏后在函数返回阶段失效。
  - 真正危险点已通过反编译锚定为 `sprintf(sp+0x18, "/www/%s", a0)`；目的缓冲区到保存 `ra` 的距离仅 `0x88` 字节，而样本中的 `request.handler_name` 长度为 `133`，足以越过该边界。
  - trace 顺序精确对应 `handle_request -> do_file -> 函数尾崩溃`，与容器日志中的 `SIGSEGV` 相互印证。
- 当前缺失的证据:
  - 未直接拿到仿真时生成的原始 HTTP 首行文本，因此 URI 前导 `/` 的字面形式只能由 `handle_request` 解析行为反推。
- 对当前现象的替代解释:
  - 其他解释（如文件内容损坏、`fopen` 失败、普通空指针）与 `0x408a94` 处返回地址加载崩溃不一致，也无法解释 `si_addr=0x77616160` 这类被输入模式污染的地址值，因此不如栈溢出解释合理。
