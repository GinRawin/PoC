# 漏洞分析: wndrmacv2-1.0.0.4 / id:000018,sig:11,src:000002,time:4555885,execs:18261,op:(null),pos:0

## 摘要

- 判定: `确认漏洞`
- Sink位置: `/usr/sbin/uhttpd sym.do_js 0x00408ae8 (jalr sprintf), 目标缓冲区 0x00408aec -> sp+0x18`
- Source位置: `/usr/sbin/uhttpd sym.handle_request 0x0040b048 (strsep 解析请求行中的路径token), 0x0040c3b8/0x0040c3f8 将其作为 s3/a0 传入 do_js`
- 漏洞二进制: `/usr/sbin/uhttpd`
- 漏洞类型: 栈缓冲区溢出 / 返回地址覆盖
- 一句话根因: `handle_request` 从请求行提取出的用户可控路径字符串被直接作为 `do_js` 的 `a0`，随后 `do_js` 用 `sprintf(sp+0x18, "/www/%s", a0)` 无边界写入 0x130 字节栈帧，覆盖保存的 `ra`，返回时跳转到攻击者构造地址 `0x6161612e`。
- 数据包字段 -> 变量赋值:
  - `request.handler_name` -> 请求路径token -> `sp+0x2730` -> `s3` -> `a0` -> `sprintf` 的 `%s`
  - `request.method = GET` -> 满足静态文件/`.js` 处理路径
  - `request.handler_name` 末尾 `.js` -> 命中 `mime_handlers` 中的 `.js` 处理项 -> `s4+0x10 = sym.do_js`
- 执行顺序:
  1. `handle_request` 用 `strsep` 从请求行缓冲区解析路径token，并保存在 `sp+0x2730`。
  2. `handle_request` 遍历 `mime_handlers`，对该路径做 `strstr` 匹配，因其包含 `.js` 而选择 `.js` handler，并在 `0x40c3f8/0x40c400` 调用 `do_js(s3, s2)`。
  3. `do_js` 在 `0x408ae8` 调用 `sprintf(sp+0x18, "/www/%s", a0)`，超长 `handler_name` 覆盖栈上的 `ra`；函数尾 `0x408c68` 取回被污染的返回地址并在 `jr ra` 后触发 `SIGSEGV`。

## 数据流细节

- 哪些数据包字段控制了哪些变量:
  - `request.handler_name` 提供了超长、以 `.js` 结尾的路径内容，进入 `handle_request` 解析后的路径token，并最终成为 `do_js` 的第一个参数。
  - `request.method = GET` 使请求走静态资源/文件处理路径，而不是 `post` 分支。
  - `request.handler_name` 中的 `.js` 后缀使 `mime_handlers` 遍历时命中 `.js` 对应处理函数 `sym.do_js`。
- 哪个函数读取了source字段:
  - `sym.handle_request` 在 `0x40b048` 开始对请求行缓冲区做 `strsep`，把路径token保存在 `sp+0x2730`；之后在 `0x40c3b8` 读回为 `s3`。
- 哪个函数写入 / 拼接 / 格式化了攻击者可控数据:
  - `sym.do_js` 在 `0x408ad8-0x408ae8` 准备 `sprintf` 参数，`a0=sp+0x18`，格式串为 `"/www/%s"`，`a2` 为来自上游的用户可控路径。
- 最终如何到达sink:

  - `-> 0x40c3f8/0x40c400` 作为 `do_js(a0=s3, a1=s2)` 调用
  - `-> 0x408ae8 sprintf(sp+0x18, "/www/%s", a0)`
  - `-> 覆盖 `sp+0x12c` 处保存的 `ra`
  - `-> 0x408c80 jr ra`
  - `-> 跳到 `0x6161612e` 崩溃`

## 误报检查

- 为什么这是一个真实漏洞，或者为什么它更像误报:
  - 崩溃不是偶然空指针。`entry_trace` 显示函数完整进入 `do_js`，并在函数尾恢复返回地址时崩溃；`si_addr=0x6161612e` 明显来自攻击者填充的 `'aaa.'` 数据，符合返回地址被覆盖后的控制流劫持模式。结合 `sprintf` 对栈缓冲区的无界写入，这是明确的真实漏洞。
- 当前缺失的证据:
  - 没有运行时寄存器转储来逐字节展示被覆盖后的 `ra`，但当前 trace、fault 地址和反汇编已经足以闭合链条。
- 对当前现象的替代解释:
  - 最合理替代解释是普通路径过长导致局部变量破坏后间接崩溃；但这仍然是同一个栈溢出漏洞，而不是误报。不存在更合理的非漏洞解释。
