# 漏洞分析: wndrmacv2-1.0.0.4 / id:000012,sig:11,src:000000,time:1939296,execs:8871,op:(null),pos:0

## 摘要

- 判定: `确认漏洞`
- Sink位置: `/usr/sbin/uhttpd handle_request@0x40afd4 0x40b7ec (jalr -> strstr)`
- Source位置: `/usr/sbin/uhttpd handle_request@0x40afd4 0x40b4dc ("Host:" 头解析分支, 0x40b528 赋值到 s6)`
- 漏洞二进制: `/usr/sbin/uhttpd`
- 漏洞类型: `NULL pointer dereference / DoS`
- 一句话根因: 请求缺失 `Host` 头时，`handle_request()` 不会给 `s6` 赋主机名；但在 `dns_hijack` 分支中仍把 `s6` 直接作为 `strstr()` 的第一个参数使用，导致对 `NULL` 解引用。
- 数据包字段 -> 变量赋值:
  - `header.Host`(缺失) -> `s6` 保持为 `0 / NULL`
  - `request.prefix + request.handler_name` -> `sp+0x2730` 中的 request-target，首字节为 `'/'`，控制流进入 `0x40b6a4`
- 执行顺序:
  1. `handle_request@0x40b4dc` 在头部循环中只在匹配到 `"Host:"` 时才执行 `s6 = s0`；本次数据包没有 `Host`，所以 `s6` 保持初始化值 `NULL`。
  2. `handle_request@0x40b650` 看到 request-target 以 `'/'` 开头，进入 `http_access_type(s6, &..., &..., s7)`；trace 命中 `0x418b48 -> 0x418cb4`，证明传入的 `a0/s6` 为 `NULL`。
  3. 返回后 `handle_request@0x40b7d0` 命中 `config_match("dns_hijack","1")`，随后在 `0x40b7ec/0x40b7f4` 调用 `strstr(s6, "routerlogin.net")`，最终触发 `SIGSEGV si_addr=NULL`。

## 数据流细节

- 哪些数据包字段控制了哪些变量:
  - `header.Host` 控制 `s6`。只有匹配到 `"Host:"` 时，代码才会在 `0x40b528` 执行 `s6 = s0`。这次 `VulPacket.json` 的 `header` 只有 `Content-Type`，没有 `Host`，所以 `s6` 保持为 `NULL`。
  - `request.prefix` 与 `request.handler_name` 共同形成 request-target，并在 `handle_request` 中被放入 `sp+0x2730`。其首字符为 `'/'`，使流程走到 `0x40b6a4` 和后续 `dns_hijack` 检查块。
  - `body.New_Language`、`body.lang_in_flash`、`body.GUI_Region`、`body.submit_flag`、`body.upgrade_yes_no` 未见进入本次 sink。
- 哪个函数读取了source字段:
  - `handle_request@0x40afd4` 通过 `fgets()` 循环读取请求头；在 `0x40b4dc` 比较 `"Host:"`，在 `0x40b504-0x40b528` 跳过空白并把值写入 `s6`。
- 哪个函数写入 / 拼接 / 格式化了攻击者可控数据:
  - `handle_request@0x40b504-0x40b528` 对 `Host:` 后的字符串做 `strspn()` 去空白后，直接把结果指针赋给 `s6`；本次因为字段缺失，没有发生该赋值，形成“未初始化后续必用”的空指针状态。
- 最终如何到达sink:
  - `handle_request` 开始时 `0x40b030` 执行 `move s6, zero`。
  - 头部循环未命中 `"Host:"`，因此 `s6` 未被覆盖。
  - `0x40b650` 判断 request-target 以 `'/'` 开头，进入 `http_access_type(s6, ...)`。
  - `http_access_type@0x418b40` 检查 `a0`；trace 实际走 `0x418b48 -> 0x418cb4`，说明 `a0 == NULL`。
  - 回到 `handle_request` 后，在 `0x40b7d0` 命中 `config_match("dns_hijack", "1")`。
  - 随后 `0x40b7ec/0x40b7f4` 调用 `strstr(s6, "routerlogin.net")`。因为 `s6 == NULL`，`strstr()` 对空指针解引用并崩溃。

## 误报检查

- 为什么这是一个真实漏洞，或者为什么它更像误报:
  - 这是一个真实漏洞。容器日志明确记录 `SIGSEGV`，trace 末尾记录 `si_addr=NULL`。
  - 更关键的是，`http_access_type` 的 trace 精确命中其空指针分支 `0x418b48 -> 0x418cb4`，这只能在调用参数 `a0 == NULL` 时发生，直接证明上游 `s6` 为 `NULL`。
  - 随后调用者又在 `0x40b7ec` 准备执行 `strstr`，并在 delay slot `0x40b7f0` 把 `s6` 送入 `a0`。这与 `si_addr=NULL` 完整吻合。
- 当前缺失的证据:
  - 没有运行时寄存器转储，无法逐寄存器打印 `jalr strstr` 当下的 `a0` 值。
  - trace 是按关键 pc 记录，最终 faulting instruction 更可能发生在 `strstr` 内部，而不是字面上的 `0x40b7e8`。
- 对当前现象的替代解释:
  - 最合理的替代解释只是“实际崩溃点在 `strstr()` 内部，而不是调用前的 `0x40b7e8` 块首地址”；这不会改变漏洞性质，也不会改变 `NULL` 源头和 sink 实参。
