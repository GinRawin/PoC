# 漏洞分析: wndrmacv2-1.0.0.4 / id:000010,sig:11,src:000003,time:1142062,execs:5705,op:(null),pos:0

## 摘要

- 判定: `确认漏洞`
- Sink位置: `/usr/sbin/uhttpd sym.config_add_qos_mac 0x4396c8 (jalr t9 -> strcmp)`
- Source位置: `/usr/sbin/uhttpd sym.config_add_qos_mac 0x4396b0/0x4396b4 (cgi_value("attached_mac"))`
- 漏洞二进制: `/usr/sbin/uhttpd`
- 漏洞类型: `NULL pointer dereference / DoS`
- 一句话根因: `config_add_qos_mac` 在读取 `attached_mac` 后未检查 `cgi_value()` 的返回值是否为 `NULL`，直接把它作为 `strcmp()` 的第一个参数使用，导致缺失该字段时崩溃。
- 数据包字段 -> 变量赋值:
  - `body.submit_flag="add_qos_mac"` -> `cgi_setobject()` 中 `s1=v0`，匹配函数表后跳转到 `sym.config_add_qos_mac (0x439658)`
  - `body.attached_mac` 缺失 -> `sym.cgi_value()` 在 `0x40cf7c` 返回 `v0=0` -> `sym.config_add_qos_mac` 中 `a0=v0` -> `strcmp(a0, "1")`
- 执行顺序:
  1. `trace/entry_trace.txt` 显示请求先进入 `sym.post_apply (0x40997c)`，解析 POST body。
  2. `sym.cgi_setobject (0x40e058)` 在 `0x40e0b8` 读取 `submit_flag`，按函数表匹配后直接进入 `sym.config_add_qos_mac (0x439658)`。
  3. `sym.config_add_qos_mac` 在 `0x4396b0` 调用 `cgi_value("attached_mac")`；该字段缺失时返回 `NULL`，随后在 `0x4396c8` 调用 `strcmp(NULL, "1")`，触发 `SIGSEGV`。

## 数据流细节

- 哪些数据包字段控制了哪些变量:
  - `body.submit_flag="add_qos_mac"` 控制 `sym.cgi_setobject` 的分发表匹配结果，决定调用 `sym.config_add_qos_mac`
  - `body.attached_mac` 是 `sym.config_add_qos_mac` 中后续 `cgi_value("attached_mac")` 读取的 source；当前样本里该字段缺失，因此 source 返回 `NULL`
  - `body.endis_traffic`、`body.upgrade_yes_no`、`body.filename` 在当前证据中没有传播到崩溃 sink，只能视为无关字段
- 哪个函数读取了source字段:
  - `sym.config_add_qos_mac` 在 `0x4396b0` 调用 `sym.cgi_value`
  - 调用点的 delay slot `0x4396b4` 把常量字符串 `0x455e54 -> "attached_mac"` 装入 `a0`
- 哪个函数写入 / 拼接 / 格式化了攻击者可控数据:
  - 到达崩溃 sink 的这条链上没有额外拼接；`sym.cgi_value` 直接返回字段值指针或 `NULL`
  - `sym.cgi_value` 内部在 `0x40cf4c-0x40cf74` 遍历 CGI 键值对，若未命中则在 `0x40cf7c` 执行 `move v0, zero`
- 最终如何到达sink:
  - `submit_flag` 先把控制流带到 `sym.config_add_qos_mac`
  - `sym.config_add_qos_mac` 在 `0x4396b0` 调用 `cgi_value("attached_mac")`
  - 当 `attached_mac` 缺失时，`sym.cgi_value` 返回 `NULL`
  - 返回后的基本块把 `v0` 直接送入 `strcmp`：`0x4396bc move a0, v0`，`0x4396cc addiu a1, a1, -0x5870` 形成常量字符串 `"1"`，`0x4396c8 jalr t9` 调用 `strcmp`
  - `strcmp(NULL, "1")` 触发空指针解引用并导致进程崩溃

## 误报检查

- 为什么这是一个真实漏洞，或者为什么它更像误报:
  - 有明确崩溃现象：`container.console.log` 和 `trace/entry_trace.txt` 都出现 `SIGSEGV`
  - 有明确控制流：trace 依次经过 `post_apply -> cgi_setobject -> config_add_qos_mac`
  - 有明确数据流：`cgi_value("attached_mac")` 找不到键时返回 `NULL`，随后该返回值被直接送入 `strcmp`
  - 崩溃点不是机械等同于最后一个 trace PC；真实危险 sink 是 `config_add_qos_mac` 内的 `strcmp` 调用点
- 当前缺失的证据:
  - 无关键缺失；确认漏洞所需的崩溃、控制流、source 返回值和 sink 调用点证据已经闭合
- 对当前现象的替代解释:
  - 另一种解释只能是 `cgi_value("attached_mac")` 在本路径上永远不会返回 `NULL`；但 `sym.cgi_value` 在 `0x40cf7c` 明确存在“未命中则返回 0”的路径，且样本包里确实缺少 `attached_mac`，因此该替代解释不成立
