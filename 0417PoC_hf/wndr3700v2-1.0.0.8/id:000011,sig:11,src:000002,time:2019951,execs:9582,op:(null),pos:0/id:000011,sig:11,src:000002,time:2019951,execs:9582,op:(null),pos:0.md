# 漏洞分析: wndr3700v2-1.0.0.8 / id:000011,sig:11,src:000002,time:2019951,execs:9582,op:(null),pos:0

## 摘要

- 判定: `确认漏洞`
- Sink位置: `/usr/sbin/uhttpd` `0x40ecac` `0x40ed64` (`strcmp($a0, "Secured")`)
- Source位置: `/usr/sbin/uhttpd` `0x40ecac` `0x40ed48` (`cgi_value("NatInboundFiltering", parsed_pairs, count)`)
- 漏洞二进制: `/mnt/sdb/hjr/HouseFuzz/data/corpus_equafl/backups/http/rehost_dir/wndr3700v2-1.0.0.8/wndr3700v2_1.0.0.8/debug/fs/usr/sbin/uhttpd`
- 漏洞类型: `NULL pointer dereference` / `DoS`
- 一句话根因: `submit_flag=wan` 命中 `wan` 分发表项后进入 `0x40ecac`，该函数对缺失的 POST 字段 `NatInboundFiltering` 调用 `cgi_value` 得到 `NULL`，随后未判空直接传给 `strcmp`，触发 `SIGSEGV`。
- 数据包字段 -> 变量赋值:
  - `body.submit_flag = "wan"` -> `0x41693c` 调用 `cgi_value("submit_flag", parsed_pairs, count)` 返回 `"wan"`，随后在分发表 `0x10000454` 命中 `wan -> 0x40ecac`
  - `body.NatInboundFiltering` `缺失` -> `0x40ed48` 调用 `cgi_value("NatInboundFiltering", parsed_pairs, count)` 返回 `NULL`，返回值进入 `$v0/$s0`
- 执行顺序:
  1. `0x406148` 解析 HTTP POST body，构造栈上的 `key/value` 对数组 `parsed_pairs`
  2. `0x41693c` 通过 `cgi_value("submit_flag", parsed_pairs, count)` 取到 `"wan"`，分发表项 `0x10000454` 将其路由到处理函数 `0x40ecac`
  3. `0x40ed48` 读取 `NatInboundFiltering`，缺失时 `cgi_value` 在 `0x4090cc` 返回 `0`
  4. `0x40ed64` 把该 `NULL` 作为第一个参数传给 `strcmp(..., "Secured")`，随后在 `entry_trace` 末尾表现为 `pc=0x40ed50` 后 `SIGSEGV si_addr=NULL`

## 数据流细节

- 哪些数据包字段控制了哪些变量:
  - `request.prefix` 的有效路径部分是 `/apply.cgi`，它只负责进入 CGI 总入口；`VulPacket.json` 中的 `handler_name = usb_approved_add` 没有在本次崩溃路径上被使用
  - `body.submit_flag = "wan"` 控制分发逻辑：`0x41693c` 读取它，`0x10000454` 的分发表项把 `"wan"` 映射到函数 `0x40ecac`
  - `body.NatInboundFiltering` 在请求体中缺失；该缺失直接决定 `0x40ed48` 的 `cgi_value` 返回 `NULL`
- 哪个函数读取了source字段:
  - `cgi_value` (`0x409060`) 负责在线性 `key/value` 数组中查找指定键；在 `0x40ed48` 被调用以读取 `NatInboundFiltering`
- 哪个函数写入 / 拼接 / 格式化了攻击者可控数据:
  - `0x406148` 将原始 POST body 解析、URL 解码并写入栈上的 `parsed_pairs`
  - 本次崩溃不是因为格式化或拷贝溢出；危险点是“缺失键 -> `NULL` 返回值”这条数据流
- 最终如何到达sink:
  - `0x406148` 解析 body -> `parsed_pairs`
  - `0x41693c` 读取 `submit_flag` 得到 `"wan"` -> 命中 `wan -> 0x40ecac`
  - `0x40ed48` 调用 `cgi_value("NatInboundFiltering", parsed_pairs, count)`，由于 body 中没有该键，`cgi_value` 走到 `0x4090cc` 返回 `0`
  - `0x40ed54/0x40ed58` 将返回值放入 `$a0/$s0`
  - `0x40ed64` 调用 `strcmp($a0, "Secured")`，`$a0 == NULL`，最终崩溃

## 误报检查

- 为什么这是一个真实漏洞，或者为什么它更像误报:
  - `container.console.log` 和 `entry_trace` 都明确显示 `SIGSEGV`
  - 崩溃前的控制流、分发表、字段读取和 sink 调用可以完全闭环，且 `cgi_value` 的未命中返回路径在本二进制内可直接核验
  - `si_addr=NULL` 与 `strcmp(NULL, "Secured")` 完全一致，不需要依赖猜测性的旧报告或符号名
- 当前缺失的证据:
  - 没有运行时寄存器转储来直接打印崩溃瞬间 `$a0=NULL`；但静态反汇编、`cgi_value` 返回路径和 `si_addr=NULL` 已足以确认
- 对当前现象的替代解释:
  - 替代解释只能是 `strcmp` 内部自身异常；但调用点唯一危险实参正是刚从 `cgi_value` 得到的 `NULL`，且请求体确实缺失 `NatInboundFiltering`，因此该替代解释不成立
