# 漏洞分析: wndr3700v2-1.0.0.8 / id:000009,sig:11,src:000036,time:1247637,execs:6119,op:(null),pos:0

## 摘要

- 判定: `确认漏洞`
- Sink位置: `/usr/sbin/uhttpd 0x0040b0b8 0x0040b178`
- Source位置: `/usr/sbin/uhttpd 0x00409060 0x004090cc`
- 漏洞二进制: `/usr/sbin/uhttpd`
- 漏洞类型: `NULL pointer dereference / DoS`
- 一句话根因: `fcn.0040b0b8` 对必需 CGI 参数 `DNSAssign` 的 `cgi_value()` 返回值未做空指针检查，直接作为 `strcpy` 源参数使用，导致 `SIGSEGV (si_addr=NULL)`。
- 数据包字段 -> 变量赋值:
  - `request.prefix="/apply.cgi?"` -> 进入 `uhttpd` 的 apply/POST 处理路径（仅控制流）
  - `body.submit_flag="bpa"` -> `sym.cgi_setobject` 中 `s1=v0`，命中 `obj.funcs` 表项 `{ "bpa", 1, 0x0040b0b8 }`
  - `body.DNSAssign` 缺失 -> `sym.cgi_value("DNSAssign", ...)` 在 `0x004090cc` 返回 `v0=0` -> `0x0040b17c` 将 `a1=v0(NULL)` -> `0x0040b178` 调用 `strcpy`
- 执行顺序:
  1. `POST /apply.cgi?` 被 `uhttpd` 解析，`sym.cgi_setobject` 在 `0x00416948` 读取 `submit_flag`。
  2. `submit_flag="bpa"` 经 `strcmp` 与 `obj.funcs` 表匹配后，在 `0x004169a4` 调用函数指针 `0x0040b0b8`。
  3. `fcn.0040b0b8` 在 `0x0040b15c` 调用 `cgi_value("DNSAssign")`，未命中时走到 `0x004090cc` 返回 `NULL`，随后 `0x0040b178` 的 `strcpy(sp+0x28, NULL)` 触发崩溃。

## 数据流细节

- 哪些数据包字段控制了哪些变量:
  - `request.prefix="/apply.cgi?"` 负责把请求送入 `uhttpd` 的 apply CGI 处理路径。
  - `body.submit_flag="bpa"` 是本次真正的控制流选择器；`sym.cgi_setobject` 先调用 `cgi_value("submit_flag")` 取值到 `s1`，再遍历 `obj.funcs` 表，最终匹配到表项 `{ name="bpa", flag=1, func=0x0040b0b8 }`。
  - `body.DNSAssign` 并未提供；这不是“值过长”问题，而是“缺失字段导致返回空指针”。
  - `body.wan_proto`、`body.wan_gateway`、`body.wan_dhcp_gateway`、`body.upgrade_yes_no` 在崩溃前没有进入 faulting 数据流；其中超长 `upgrade_yes_no` 不是这次崩溃根因。
  - `request.handler_name="SetWANRenew"` 仅存在于 `VulPacket.json` 元数据中；当前 trace/反汇编没有证明它参与了本次实际控制流选择，真正被代码读取并决定分发的是 `submit_flag`。
- 哪个函数读取了source字段:
  - `sym.cgi_value` (`0x00409060`) 读取 CGI 键值对。对 `DNSAssign` 的查询由 `0x0040b15c` 发起，未命中时在 `0x004090cc` 返回 `v0=0`。
- 哪个函数写入 / 拼接 / 格式化了攻击者可控数据:
  - 本次不是“把攻击者字符串拷入小缓冲区”的溢出，而是把 `cgi_value()` 的返回指针直接作为 `strcpy` 源参数使用。
  - `fcn.0040b0b8` 在 `0x0040b168` 准备目标缓冲区 `a0=s2(sp+0x28)`，在 `0x0040b17c` 把 `a1=v0`，随后 `0x0040b178` 调用 `strcpy`。
- 最终如何到达sink:
  - `body.submit_flag="bpa"` -> `sym.cgi_setobject` 命中 `bpa` 表项 -> 调用 `0x0040b0b8`
  - `body.DNSAssign` 缺失 -> `cgi_value("DNSAssign")` 返回 `NULL`
  - `NULL` 经返回寄存器 `v0` 直接流入 `strcpy` 的 `a1`
  - `strcpy` 解引用空指针，进而产生 `SIGSEGV`

## 误报检查

- 为什么这是一个真实漏洞，或者为什么它更像误报:
  - 这是一个真实漏洞。`container.console.log` 明确记录 `SIGSEGV CAUGHT!`，`trace/entry_trace.txt` 末尾明确显示 `--- SIGSEGV {si_addr=NULL} ---`。
  - trace 顺序与反汇编完全对齐: `0x0040b15c` 调 `cgi_value("DNSAssign")`，trace 命中 `0x004090cc` 后返回到 `0x0040b164`，紧接着走向 `strcpy` 调用点并崩溃。
  - 可替代解释里最像的是“`upgrade_yes_no` 超长导致溢出”，但这与 trace 不符，因为崩溃发生在第一次读取 `DNSAssign` 之后，根本没走到使用 `upgrade_yes_no` 的路径。
- 当前缺失的证据:
  - 没有影响判定的关键缺失证据。唯一不确定的是 `0x0040b0b8` 的高层业务函数名已被 strip，但其被 `submit_flag="bpa"` 命中、且内部首个危险点是 `DNSAssign` 的空指针传入 `strcpy`，证据已经充分。
- 对当前现象的替代解释:
  - 最合理的替代解释是“业务逻辑假定 `DNSAssign` 必填，缺字段只是触发了非预期异常退出”；但这仍然是远程可触发的空指针解引用，不能据此降为误报。
