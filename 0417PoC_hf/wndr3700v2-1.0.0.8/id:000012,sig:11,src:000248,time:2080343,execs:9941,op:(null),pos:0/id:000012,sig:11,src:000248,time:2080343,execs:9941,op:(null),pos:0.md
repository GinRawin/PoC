## 摘要

- 判定: `确认漏洞`
- Sink位置: `uhttpd fcn.0040ad34 0x40ade0 (jalr -> strcpy)` 
- Source位置: `uhttpd fcn.0040ad34 0x40adc8 (call sym.cgi_value("DNSAssign")) -> sym.cgi_value 0x4090cc (未命中字段时返回 NULL)`
- 漏洞二进制: `/usr/sbin/uhttpd`
- 漏洞类型: `NULL pointer dereference / remote DoS`
- 一句话根因: `pptp` 配置处理函数 `fcn.0040ad34` 未检查 `cgi_value("DNSAssign")` 的返回值，直接把 `NULL` 作为 `strcpy` 的源参数使用，导致 `SIGSEGV`。
- 数据包字段 -> 变量赋值:
  - `body.submit_flag = "pptp"` -> `sym.cgi_setobject` 中 `s1 = cgi_value("submit_flag", ...)`，随后匹配 `funcs` 表中的 `"pptp"` 项并调用 `0x40ad34`
  - `body.DNSAssign` 缺失 -> `fcn.0040ad34` 中 `v0 = cgi_value("DNSAssign", ...) = NULL` -> `a1 = v0` -> `strcpy(sp+0x30, NULL)`
- 执行顺序:
  1. `POST / apply.cgi?/top.html timestamp=` 请求进入 `uhttpd`，trace 落入 `sym.cgi_setobject@0x4168ec`
  2. `sym.cgi_setobject` 调用 `cgi_value("submit_flag")` 取到 `"pptp"`，在 `obj.funcs` 表中命中 `"pptp" -> 0x40ad34`
  3. `fcn.0040ad34` 调用 `cgi_value("DNSAssign")` 得到 `NULL`，随后在 `0x40ade0` 调用 `strcpy` 时崩溃

## 数据流细节

- 哪些数据包字段控制了哪些变量:
  - `request.handler_name = "apply.cgi?/top.html timestamp="` 使请求落到本次 trace 所示的 `cgi_setobject` 配置处理路径
  - `body.submit_flag = "pptp"` 控制 `sym.cgi_setobject` 在 `obj.funcs` 表中选择 `"pptp"` 对应回调 `0x40ad34`
  - `body.DNSAssign` 本应提供给 `fcn.0040ad34` 的第一个配置字符串；本样本中该字段缺失，因此 `cgi_value("DNSAssign")` 返回 `NULL`
- 哪个函数读取了source字段:
  - `sym.cgi_value@0x409060` 负责在请求键值表中查找字段；匹配命中时在 `0x4090c0` 取出值指针，未命中时在 `0x4090cc` 返回 `0`
- 哪个函数写入 / 拼接 / 格式化了攻击者可控数据:
  - `fcn.0040ad34` 在 `0x40ade0`、`0x40ae10`、`0x40ae40` 等处用 `strcpy` 把 `cgi_value(...)` 返回的字符串复制到栈缓冲区；本次在第一次 `strcpy` 前就因源指针为 `NULL` 崩溃
- 最终如何到达sink:
  - `body.submit_flag="pptp"` -> `sym.cgi_setobject` 命中 `"pptp"` 表项 `{0x43c7d4 "pptp", 1, 0x40ad34}`
  - 进入 `fcn.0040ad34`
  - `cgi_value("DNSAssign", req, ...)` 未找到 `body.DNSAssign` -> `v0 = NULL`
  - `0x40add8 move a0, s2; 0x40addc load strcpy; 0x40ade0 jalr t9`，delay slot `0x40ade4 move a1, v0`
  - `strcpy(dst=sp+0x30, src=NULL)` 触发空指针解引用并导致 `SIGSEGV`

## 误报检查

- 为什么这是一个真实漏洞，或者为什么它更像误报:
  - 这是一个真实崩溃。容器日志和入口 trace 都显示 `SIGSEGV`，且 `si_addr=NULL`。反汇编显示在 `pptp` 分支中，`cgi_value("DNSAssign")` 的返回值未经判空直接作为 `strcpy` 源参数使用，和空指针崩溃完全一致。
- 当前缺失的证据:
  - `request.handler_name` 到 `cgi_setobject` 的更早期 URL 分发代码未单独反编译，但当前 trace 已经直接证明该请求实际执行到了 `cgi_setobject`，不影响本次 `source -> sink` 链闭合。
- 对当前现象的替代解释:
  - 替代解释不成立。`strcpy` 目的缓冲区 `s2 = sp+0x30` 由 `memset` 初始化，栈指针正常；最符合 `si_addr=NULL` 且执行序列的解释只有 `cgi_value("DNSAssign")` 返回 `NULL` 后被传入 `strcpy`。
