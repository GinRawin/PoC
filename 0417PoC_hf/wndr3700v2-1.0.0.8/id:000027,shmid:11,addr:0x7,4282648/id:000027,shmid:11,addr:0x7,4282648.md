# 漏洞分析: wndr3700v2-1.0.0.8 / id:000027,shmid:11,addr:0x7,4282648

## 摘要

- 判定: `确认漏洞`
- Sink位置: `/usr/sbin/uhttpd` `0x4234c0` `0x423500 (sprintf)`
- Source位置: `/usr/sbin/uhttpd` `0x4158e4` `0x4158fc`
- 漏洞二进制: `/usr/sbin/uhttpd`
- 漏洞类型: 栈缓冲区溢出
- 一句话根因: `uhttpd` 将请求体 `select_approved_item` 原样作为 `%s` 传入 `sprintf(sp+0x18, "/sbin/hotplug2.testbusy USB_approved_device%s", attacker)`，目标栈缓冲区仅 `0x80` 字节，导致返回地址区域被覆盖，并在函数返回时跳到 `0x61616160` 崩溃。
- 数据包字段 -> 变量赋值:
  - `body.select_approved_item` -> `0x415914` 写入全局槽 `*(global-0x3c1c)`，随后在 `0x416ddc` 作为 `a0` 传给 `0x4235d4`
  - `body.submit_flag=usb_approved_del` -> 命中删除已批准 USB 设备的处理路径，trace 实际进入 `0x416dd4 -> 0x4235d4 -> 0x4234c0`
  - `request.prefix=/apply.cgi?` -> 命中 CGI 分发路径并进入本次处理逻辑
- 执行顺序:
  1. `POST /apply.cgi?` 携带 `submit_flag=usb_approved_del` 与超长 `select_approved_item` 进入 `uhttpd`
  2. `0x4158fc` 以键名 `select_approved_item` 读取请求字段，并在 `0x415914` 保存到全局变量
  3. `0x416dd4` 取出该全局指针作为参数调用 `0x4235d4`
  4. `0x4235fc` 再调用 `0x4234c0(a0=user_ptr)`；`0x423500` 用 `sprintf` 把攻击者字符串写入 `sp+0x18`
  5. 长度 `43 + 512 = 555` 字节的数据覆盖 `0x80` 字节局部缓冲区及保存的寄存器/返回地址，`system()` 返回后在函数退出阶段跳转到 `0x61616160` 并触发 `SIGSEGV`

## 数据流细节

- 哪些数据包字段控制了哪些变量:
  - `body.select_approved_item` 控制 `0x415914` 写入的全局指针 `*(global-0x3c1c)`，并一路作为 `0x4235d4`/`0x4234c0` 的实参
  - `body.submit_flag=usb_approved_del` 控制 CGI 选择器，保证走到 USB approved delete 处理路径
  - `request.prefix=/apply.cgi?` 保证进入 CGI 处理入口，而不是静态文件路径
- 哪个函数读取了source字段:
  - `0x4158e4` 开始的函数在 `0x4158fc` 以只读字符串 `select_approved_item` 作为键读取请求字段；返回指针在 `0x415914` 被保存到全局槽 `-0x3c1c`
- 哪个函数写入 / 拼接 / 格式化了攻击者可控数据:
  - `0x4234c0` 在 `0x423500` 调用 `sprintf`，格式串是 `"/sbin/hotplug2.testbusy USB_approved_device%s"`，目标缓冲区是 `sp+0x18`，调用前仅在 `0x4234e8` 用 `memset(..., 0, 0x80)` 初始化了 `0x80` 字节
- 最终如何到达sink:
  - `select_approved_item` -> `0x415914` 全局槽 -> `0x416ddc` 载入到 `a0` -> `0x4235fc` 调 `0x4234c0(a0)` -> `0x423500 sprintf(sp+0x18, fmt, a0)` -> 覆盖保存的 `ra` -> `system()` 返回后在尾声跳转到 `0x61616160`

## 误报检查

- 为什么这是一个真实漏洞，或者为什么它更像误报:
  - 这是实打实的栈溢出。容器日志与 trace 同时给出 `SIGSEGV`；trace 还给出 `si_addr=0x61616160`，与输入中的 `a` 模式一致。反汇编显示崩溃前唯一直接消费攻击者字符串的危险写入是 `0x423500 sprintf`，且其目标缓冲区固定只有 `0x80` 字节。实际请求值长度 `512`，拼接固定前缀后总长度 `555`，必然越界。
- 当前缺失的证据:
  - 无影响结论的关键缺失。个别内部函数符号名未知，但 source、变量、sink、trace 路径和崩溃地址已经闭环。
- 对当前现象的替代解释:
  - 更合理的替代解释不存在。`/bin/sh` 子进程在 `trace/34_tb_log.txt` 中是 `exit(1)`，真正的 `SIGSEGV` 发生在 `uhttpd` 父进程返回路径，符合栈返回地址被覆盖后的行为，而不是脚本自身崩溃或环境误报。
