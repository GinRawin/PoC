## 摘要

- 判定: `确认漏洞`
- Sink位置: `/usr/sbin/uhttpd` `0x40b4c4` `0x40b56c` (`strcpy`, 调用时 `a1=v0=NULL`)
- Source位置: `/usr/sbin/uhttpd` `0x409060` `0x4090c0/0x4090cc` (`cgi_value` 从 CGI KV 表取值，未命中时返回 `NULL`)
- 漏洞二进制: `/usr/sbin/uhttpd`
- 漏洞类型: 空指针解引用
- 一句话根因: `submit_flag` 命中对应 handler 后，该 handler 直接将 `cgi_value("DNSAssign", ...)` 的返回值传给 `strcpy`，未检查字段缺失时的 `NULL`。
- 数据包字段 -> 变量赋值:
  - `body.submit_flag=ether` -> `s1=v0` in `cgi_setobject` (`0x416954`)，用于命中后续 handler
  - `body.DNSAssign` 缺失 -> `v0=0` in `cgi_value` (`0x4090cc`)，再作为 `strcpy` 的源参数 `a1`
- 执行顺序:
  1. 请求进入 `/usr/sbin/uhttpd`，`cgi_setobject` 先通过 `cgi_value("submit_flag", ...)` 取到 `ether`
  2. `submit_flag=ether` 让控制流进入 `0x40b4c4` 对应的配置 handler
  3. 该 handler 调用 `cgi_value("DNSAssign", ...)` 未命中返回 `NULL`，随后在 `0x40b56c` 调 `strcpy` 时将 `NULL` 作为源指针，触发 `SIGSEGV`

## 误报检查

- 为什么这是一个真实漏洞，或者为什么它更像误报:
  - 崩溃证据明确: 容器日志为 `SIGSEGV CAUGHT!`，入口 trace 末尾是 `--- SIGSEGV ... si_addr=NULL ---`
  - 静态链条闭合: `submit_flag` 命中 handler，`DNSAssign` 缺失使 `cgi_value` 返回 `NULL`，`NULL` 直接传给 `strcpy`
  - 崩溃发生在真实危险调用点附近，不是单纯仿真退出或无害断言
- 当前缺失的证据:
  - 没有运行时寄存器转储，无法给出崩溃瞬间 libc `strcpy` 内部 PC
  - 当前 handler 的符号名不可直接恢复，只能精确到 `0x40b4c4`
- 对当前现象的替代解释:
  - 最合理的替代解释是 CGI 解析阶段丢失了 `DNSAssign` 键值，但这并不改变漏洞结论，因为 sink 侧确实未做 `NULL` 检查；无论字段本身缺失还是被前序解析丢弃，最终都是可由请求触发的空指针解引用
