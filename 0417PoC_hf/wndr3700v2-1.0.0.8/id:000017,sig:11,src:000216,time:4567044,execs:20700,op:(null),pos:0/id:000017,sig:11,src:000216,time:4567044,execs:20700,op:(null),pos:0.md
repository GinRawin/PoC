# 漏洞分析: wndr3700v2-1.0.0.8 / id:000017,sig:11,src:000216,time:4567044,execs:20700,op:(null),pos:0

## 摘要

- 判定: `确认漏洞`
- Sink位置: `/usr/sbin/uhttpd` `qos_del handler @ 0x40f8f8` `0x40f978 (lb v1, (s2))`
- Source位置: `/usr/sbin/uhttpd` `qos_del handler @ 0x40f8f8` `0x40f954 (cgi_value("select_del", ...) 返回值写入 s2 于 0x40f950)`
- 漏洞二进制: `/mnt/sdb/hjr/HouseFuzz/data/corpus_equafl/backups/http/rehost_dir/wndr3700v2-1.0.0.8/wndr3700v2_1.0.0.8/debug/fs/usr/sbin/uhttpd`
- 漏洞类型: `NULL pointer dereference / DoS`
- 一句话根因: `submit_flag=qos_del` 选中 `qos_del` 处理函数后，代码对 `cgi_value("select_del", ...)` 的返回值缺少 NULL 检查，直接在 `0x40f978` 解引用，导致 SIGSEGV。
- 数据包字段 -> 变量赋值:
  - `body.submit_flag="qos_del"` -> `cgi_setobject()` 中的 `s1`，并匹配全局函数表项 `qos_del -> 0x40f8f8`
  - `body.select_del` 缺失 -> `cgi_value("select_del", ...)` 返回 `v0=NULL` -> `s2=NULL`
  - `body.select_del_mac` 缺失 -> `cgi_value("select_del_mac", ...)` 返回值进入 `del_items("qos_mac_list", ...)`，但不是本次崩溃的直接原因
- 执行顺序:
  1. 请求进入 `/apply.cgi?` 路径，`cgi_setobject()` 在 `0x416948` 读取 `submit_flag`。
  2. `submit_flag="qos_del"` 在函数表 `0x10000730` 命中 `qos_del -> 0x40f8f8`，进入对应处理函数。
  3. 处理函数读取缺失的 `select_del`，得到 `NULL` 存入 `s2`，随后在 `0x40f978` 执行 `lb (s2)` 触发 `SIGSEGV`。

## 数据流细节

- 哪些数据包字段控制了哪些变量:
  - `request.prefix="/apply.cgi?"` 使请求进入 `do_apply/cgi_setobject` 这一路径。
  - `body.submit_flag="qos_del"` 控制 `cgi_setobject()` 对函数表的选择，决定调用 `0x40f8f8`。
  - `body.select_del` 是 `qos_del` handler 的关键 source 字段；本样本中该字段缺失，因此 source 值为 `NULL`。
  - `body.hidden_name`、`body.%20timestamp` 在当前崩溃链中没有证据流入 sink。
- 哪个函数读取了source字段:
  - `sym.cgi_value` (`0x409060`) 读取 CGI 参数；在 `0x40f954` 被以键名 `select_del` 调用，返回值写入 `s2`。
- 哪个函数写入 / 拼接 / 格式化了攻击者可控数据:
  - 本链条里不存在额外拼接或格式化。`select_del` 的值由 `cgi_value()` 直接以指针形式返回给 `qos_del` handler。
  - `sym.del_items` (`0x4092d8`) 只是消费该指针并处理配置项；真正触发崩溃的是返回后的空指针解引用。
- 最终如何到达sink:
  - `cgi_setobject()` 在 `0x416948` 取到 `submit_flag`，用 `strcmp` 在函数表中查找。
  - 数据段 `0x10000730` 明确包含表项 `0x0043cab0 ("qos_del"), 0x00000012, 0x0040f8f8`，说明 `qos_del` 会调用 `0x40f8f8`。
  - `0x40f954` 处 `cgi_value("select_del", ...)` 返回 `NULL`，`0x40f950` 把 `v0` 保存到 `s2`。
  - `0x40f978` 紧接着执行 `lb v1, (s2)`；结合 trace 末尾 `--- SIGSEGV ... si_addr=NULL ---`，可确认 sink 为对 `NULL` 的字节读取。

## 误报检查

- 为什么这是一个真实漏洞，或者为什么它更像误报:
  - 这是一个真实漏洞。容器日志明确捕获 `SIGSEGV`，入口 trace 精确落到 `0x40f974` 附近，且反汇编表明实际 faulting instruction 是 `0x40f978` 的 `lb (s2)`。
  - 崩溃不是仿真噪声，也不是 trace 误对齐，因为 `si_addr=NULL` 与 `cgi_value("select_del") -> NULL -> s2` 的数据流完全一致。
- 当前缺失的证据:
  - 没有单独的运行时 CGI 参数转储，无法看到服务器内部解析后的参数表内容；但这不影响结论，因为 `cgi_value` 的返回值、trace 顺序和 `si_addr=NULL` 已经足够闭环。
- 对当前现象的替代解释:
  - 最合理的替代解释是 CGI 解析器未生成 `select_del` 项，而不是字段内容本身破坏了内存。也就是说，本次触发条件的核心是“缺少必需字段后的空指针解引用”，不是溢出或 UAF。
