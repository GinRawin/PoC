# 漏洞分析: wndr3700v2-1.0.0.8 / id:000013,sig:11,src:000310,time:2354503,execs:11084,op:(null),pos:0

## 摘要

- 判定: `确认漏洞`
- Sink位置: `/usr/sbin/uhttpd` `0x40f7bc` `0x40f82c`
- Source位置: `/usr/sbin/uhttpd` `0x40f7bc` `0x40f814`
- 漏洞二进制: `/usr/sbin/uhttpd`
- 漏洞类型: `NULL pointer dereference` / 拒绝服务
- 一句话根因: `add_qos_mac` 处理函数在读取 `attached_mac` 失败后，未检查 `lookup("attached_mac", ...)` 的返回值是否为 `NULL`，直接把它作为字符串比较函数的第一个实参使用，导致 `SIGSEGV`。
- 数据包字段 -> 变量赋值:
  - `body.submit_flag = "add_qos_mac"` -> `0x41694c` 调用 `0x409060` 查出 `submit_flag` 对应值，`0x416954` 将返回值写入 `s1`，随后在 `0x4169d8` 与调度表项比较并命中 `add_qos_mac -> 0x40f7bc`
  - `body.attached_mac` 缺失 -> `0x40f814` 调用 `0x409060` 按键名 `"attached_mac"` 查找参数，返回 `v0 = NULL`
  - `v0 = NULL` -> `0x40f820` 将 `v0` 送入 `a0`，`0x40f82c` 调用字符串比较函数与常量 `"1"` 比较，触发空指针解引用
- 执行顺序:
  1. 请求进入 `/usr/sbin/uhttpd`，`trace/entry_trace.txt` 显示控制流进入 `0x4168ec`；这里先读取 `submit_flag`，并在表项 `0x10000718` 命中 `add_qos_mac -> 0x40f7bc`
  2. `0x40f7bc` 处理 `add_qos_mac`，先执行辅助逻辑，然后在 `0x40f814` 再次通过 `0x409060` 查找 `"attached_mac"`
  3. 由于样本中没有 `body.attached_mac`，查找返回 `NULL`；随后 `0x40f82c` 对 `NULL` 执行字符串比较，`trace` 末尾停在 `0x40f81c` 后抛出 `SIGSEGV si_addr=NULL`

## 数据流细节

- 哪些数据包字段控制了哪些变量:
  - `request.prefix = "/apply.cgi?"` 使请求落入 CGI 处理路径
  - `body.submit_flag = "add_qos_mac"` 控制 `0x4168ec` 的表驱动分发，决定进入 `0x40f7bc`
  - `body.attached_mac` 是 `0x40f7bc` 中被直接读取的必需字段；本样本里该字段缺失，所以 `0x409060` 返回 `NULL`
  - `request.handler_name = "wan_intr_netmask"` 与 `body.internet_ppp_type`、`body.internet_type`、`body.upgrade_yes_no`、`body.%20timestamp` 在已观察到的崩溃链中没有进入 sink；它们不是这次空指针崩溃的关键触发字段
- 哪个函数读取了source字段:
  - `0x409060`。其逻辑是遍历 `(key, value)` 数组，对每个元素调用字符串比较；若比较结果为 0，则返回该元素的 value 指针，否则继续遍历，最终未命中时返回 `0`
  - 在本次漏洞链中，`0x40f814` 以 `"attached_mac"` 作为查找键调用 `0x409060`，这是 source 对应的真实读取点
- 哪个函数写入 / 拼接 / 格式化了攻击者可控数据:
  - 这条崩溃链不依赖复杂拼接。危险值不是经过格式化后溢出，而是 `0x409060` 直接把缺失字段表示为 `NULL`
  - `0x40f3d0` 和 `0x4091a8` 只是在崩溃前构造 `qos_mac_list...` 相关辅助字符串；它们出现在 trace 中，但不是根因
- 最终如何到达sink:
  - `0x4168ec` 先通过 `submit_flag` 选中 `add_qos_mac`
  - `0x40f7bc` 复用同一组参数数组 `(s0, s1)`，在 `0x40f814` 查找 `"attached_mac"`
  - 样本体中缺少 `attached_mac`，所以 `v0 = NULL`
  - `0x40f820` 把 `v0` 放入 `a0`
  - `0x40f824` 把常量地址 `0x43dd4c` 装入 `a1`；该地址对应字符串 `"1"`
  - `0x40f82c` 调用字符串比较函数，实际效果等价于 `strcmp(NULL, "1")`

## 误报检查

- 为什么这是一个真实漏洞，或者为什么它更像误报:
  - `container.console.log` 明确记录了 `[GreenHouseQEMU] SIGSEGV CAUGHT!`
  - `trace/entry_trace.txt` 末尾明确记录 `--- SIGSEGV {si_addr=NULL} ---`
  - 崩溃前最后一段本地代码能精确解释为: 查找 `attached_mac` -> 返回 `NULL` -> 将 `NULL` 作为字符串比较函数实参
  - 同一参数数组此前已经成功解析出 `submit_flag` 并完成 handler 分发，说明不是整个请求解析失败，也不是 trace 噪声
- 当前缺失的证据:
  - 没有再向前恢复 HTTP 解析器把原始 POST body 变成 `(key, value)` 数组的内部符号名
  - 但这不影响判定，因为 handler 内部对 `"submit_flag"` 和 `"attached_mac"` 的二次查找已经直接证明了控制字段和值字段的使用方式
- 对当前现象的替代解释:
  - 最合理的替代解释是参数数组损坏而非字段缺失
  - 但这与现有证据不符: `submit_flag` 查找成功、调度表命中正确、崩溃地址稳定落在 `"attached_mac"` 查找后的比较点，因此“缺失必需字段导致空指针解引用”是更强解释
