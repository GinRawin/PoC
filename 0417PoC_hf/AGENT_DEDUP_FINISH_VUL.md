# 去除已报告漏洞任务模板

你需要判断“当前待检查固件目录”中的哪些漏洞，其实已经被“已完成漏洞报告目录”中的历史报告覆盖，并把这些待删除的漏洞子目录名写入 `tobedeleted.json`。

## 输入信息

运行命令时会额外告诉你三项路径：

1. 当前待检查固件目录：`<CURRENT_FIRMWARE_DIR>`
2. 对应的已完成漏洞报告目录：`<FINISH_FIRMWARE_DIR>`
3. 结果输出文件：`<CURRENT_FIRMWARE_DIR>/tobedeleted.json`

## 必做步骤

1. 读取 `<CURRENT_FIRMWARE_DIR>` 下每个一级子目录中的 markdown 文件。
2. 对每个漏洞子目录，总结其核心信息：
   - 漏洞类型
   - 受影响二进制/源码位置
   - 触发接口、路由、CGI、表单或处理函数
   - 关键参数、危险函数、调用链和根因
   - 利用方式、约束条件、是否需要认证、触发结果
3. 读取 `<FINISH_FIRMWARE_DIR>` 下所有已有漏洞子目录中的 markdown 文件，并同样提取上述关键信息。
4. 逐项比对，判断当前待检查目录中的漏洞是否已经被已完成目录里的某份报告覆盖。

## 比对原则

判断“已被报告”时，必须基于漏洞本身的技术事实，而不是基于目录名是否相似。

优先依据以下信号综合判断：

- 是否落在同一个处理入口、同一个路由/CGI/接口或同一条功能链路
- 是否针对同一个危险函数、同一段关键代码或同一处根因
- 是否由同一组关键参数或同类输入控制触发
- 是否属于同一个漏洞行为，例如同一处命令注入、缓冲区溢出、栈溢出、格式化字符串等
- 是否只是不同 crash 样本、不同输入变体、不同 PoC，但本质指向同一漏洞

以下情况不要判成“已报告”：

- 只是同一固件中的不同漏洞
- 同一个组件里但代码位置、危险函数、根因或触发路径明显不同
- 结论描述过于模糊，无法确认是同一个漏洞

如果证据不足，请保守处理，不要误删。

## 输出要求

1. 把确认“已被报告”的漏洞子目录名写入 `<CURRENT_FIRMWARE_DIR>/tobedeleted.json`。
2. 文件内容必须是 JSON 字符串数组，例如：

```json
[
  "id:000009,shmid:000003,cmdinj,src:000094,time:268478,execs:3514,op:(null),pos:0,ipc:3",
  "id:000002,sig:11,src:000002,time:20704,execs:175,op:(null),pos:0"
]
```

3. 如果没有任何已报告漏洞，写入空数组：

```json
[]
```

4. `tobedeleted.json` 中只能放“当前待检查固件目录”下的一级漏洞子目录名，不要写绝对路径，不要写说明文字，不要输出 Markdown。

## 额外限制

- 只处理当前命令指定的那个固件目录，不要改动其他固件目录。
- 除了写入 `tobedeleted.json` 外，不要修改现有 markdown 内容。
- 开始写入 `tobedeleted.json` 前，先完成阅读和比对，不要边读边猜。
