# 漏洞分析: r6900-v1.0.2.26-10.0.45 / id:000002,sig:11,src:000282,time:8112495,execs:118444,op:splice,rep:2

## 摘要

- 判定: `确认漏洞`
- Sink位置: `/usr/sbin/httpd` `0x000501f4` `0x00050270 (strcpy@plt)`，第二次 `strtok_r` 返回 `NULL` 后执行 `strcpy(dst, NULL)`
- Source位置: `/usr/sbin/httpd` `0x00050560` `0x00050588/0x0005059c/0x000505bc/0x00050638/0x00050654`，从请求中读取 `schedule_day`、`time_zone`、`schedule_daylightadjust`、`starthour`、`startminute`
- 漏洞二进制: `/usr/sbin/httpd`
- 漏洞类型: 空指针解引用 / 拒绝服务
- 一句话根因: `fwSchedulePPP2.cgi` 在请求缺失调度字段时仍把空字符串格式化为 `pppoe2_schedule_config="0::::"`，随后解析函数假定该配置一定有 5 个 `:` 分隔 token，未检查 `strtok_r` 返回值就连续 `strcpy`，导致 `NULL` 被传入 `strcpy`
- 数据包字段 -> 变量赋值:
  - `request.handler_name = "fwSchedulePPP2.cgi"` -> CGI 分发表项 `[0x00161490]` -> handler `0x00050560`
  - `body.schedule_day` 缺失 -> 栈缓冲区 `sp+0x814` 为空串 -> `atoi("") == 0`
  - `body.time_zone` 缺失 -> 栈缓冲区 `sp+0x614` 为空串
  - `body.schedule_daylightadjust` 缺失 -> 栈缓冲区 `sp+0x514` 为空串
  - `body.starthour` 缺失 -> 栈缓冲区 `sp+0x414` 为空串
  - `body.startminute` 缺失 -> 栈缓冲区 `sp+0x314` 为空串
  - 上述变量 -> `sprintf("%d:%s:%s:%s:%s")` -> `pppoe2_schedule_config = "0::::"`
- 执行顺序:
  1. `POST /fwSchedulePPP2.cgi` 命中 `httpd` 内部分发表，进入 handler `0x00050560`
  2. handler 从请求中读取 5 个调度字段；由于 body 为空，这些字段为空串，随后拼接并写入 NVRAM 键 `pppoe2_schedule_config`
  3. handler 继续调用 `0x000501f4` 解析该配置；第二次 `strtok_r` 返回 `NULL`，`0x00050270` 执行 `strcpy(dst, NULL)`，进程收到 `SIGSEGV`

## 数据流细节

- 哪些数据包字段控制了哪些变量:
  - `request.handler_name` 控制控制流是否进入 `fwSchedulePPP2.cgi -> 0x00050560`
  - 空 `body` 使 `schedule_day`、`time_zone`、`schedule_daylightadjust`、`starthour`、`startminute` 均缺失，进而分别落入 handler 的 5 个局部缓冲区为空串
  - `schedule_day` 经过 `atoi` 变成整数 `0`，其余 4 个字段保持空串
- 哪个函数读取了source字段:
  - handler `0x00050560` 多次调用 `0x0001a3b8` 读取请求参数，读取的键名分别是 `schedule_day`、`schedule_alldayenable`、`time_zone`、`schedule_daylightadjust`、`starthour`、`startminute`、`endhour`、`endminute`
- 哪个函数写入 / 拼接 / 格式化了攻击者可控数据:
  - `0x00050560` 在 `0x00050760` 调用 `sprintf@plt`，格式串为 `"%d:%s:%s:%s:%s"`，目标缓冲区为 `sp+0x914`
  - 紧接着 `0x0005076c` 调用 `acosNvramConfig_set@plt`，把该格式化结果写入键 `pppoe2_schedule_config`
- 最终如何到达sink:
  - `0x000501f4` 在 `0x00050228` 读取 `pppoe2_schedule_config`
  - `0x00050244` 第一次 `strtok_r(..., ":")` 取得 `"0"`，`0x00050250` 安全复制
  - 因配置串是 `"0::::"`，`0x00050264` 第二次 `strtok_r` 返回 `NULL`
  - `0x00050270` 直接执行 `strcpy(dst, r1)`，此时 `r1 == NULL`，触发空指针解引用

## 误报检查

- 为什么这是一个真实漏洞，或者为什么它更像误报:
  - 控制台有明确 `Segmentation fault (core dumped)`，`trace/12_tb_log.txt` 也记录了 `SIGSEGV` 且 `si_addr=NULL`
  - `fwSchedulePPP2.cgi` 的 handler 和后续解析函数之间存在完整、可验证的 `source -> variable -> sink` 链：缺失请求字段 -> 空串局部变量 -> `pppoe2_schedule_config="0::::"` -> `strtok_r` 返回 `NULL` -> `strcpy(dst, NULL)`
  - 真正危险实参不是“请求本身”而是被格式化后写回 NVRAM 的配置串；这一点已通过 `0x00050760 -> 0x0005076c -> 0x000501f4 -> 0x00050270` 的调用序列核实
- 当前缺失的证据:
  - trace 没有给出崩溃时的精确 pc，因此无法用动态证据直接写出 `pc=0x50270`
  - `0x0001a3b8` 的符号名未知，只能根据调用约定和键名确认它是请求参数读取例程
- 对当前现象的替代解释:
  - 最合理的替代解释是其它后台逻辑在保存配置后触发了无关崩溃；但 `SIGSEGV si_addr=NULL` 与 `0x000501f4` 中确定存在的 `strcpy(dst, NULL)` 高度吻合，而本请求又正好构造出 `"0::::"` 这种缺 token 配置，因此替代解释明显更弱
