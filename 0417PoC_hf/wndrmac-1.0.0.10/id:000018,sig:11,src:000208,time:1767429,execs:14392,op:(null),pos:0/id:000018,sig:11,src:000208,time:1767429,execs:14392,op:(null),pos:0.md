# 漏洞分析: wndrmac-1.0.0.10 / id:000018,sig:11,src:000208,time:1767429,execs:14392,op:(null),pos:0

## 摘要

- 判定: `确认漏洞`
- Sink位置: `uhttpd sym.config_qosmac_del(0x43ef30) 0x43efb0`
- Source位置: `uhttpd sym.config_qosmac_del(0x43ef30) 0x43ef8c`
- 漏洞二进制: `/usr/sbin/uhttpd`
- 漏洞类型: `NULL` 指针解引用
- 一句话根因: `POST /apply.cgi` 在 `submit_flag=qos_delmac` 时进入 `config_qosmac_del`，该函数对 `cgi_value("select_editnum_mac", ...)` 的返回值未做空指针检查，直接在 `0x43efb0` 读取首字节导致 `SIGSEGV`。
- 数据包字段 -> 变量赋值:
  - `request.method=POST` + `request.prefix=/apply.cgi?` -> 进入 `sym.post_apply` / `sym.cgi_setobject`
  - `body.submit_flag="qos_delmac"` -> `sym.cgi_setobject` 中的 `s1` 比较键，命中后经 `0x40f7ec/0x40f808` 跳转到 `sym.config_qosmac_del`
  - `body.select_editnum_mac` 缺失 -> `sym.config_qosmac_del` 在 `0x43ef8c` 调用 `cgi_value("select_editnum_mac", ...)` 返回 `v0=NULL`，随后 `0x43ef88` 把该值写入 `s2`
- 执行顺序:
  1. `POST /apply.cgi?` 请求进入 `sym.post_apply(0x40a6c0)`，trace 命中 `0x40a6c0 -> 0x40aa14`
  2. `sym.post_apply` 在 `0x40aa18` 调用 `sym.cgi_setobject(0x40f754)`，后者按 `submit_flag` 遍历动作表
  3. 命中 `qos_delmac` 后从 `0x40f7ec/0x40f808` 跳到 `sym.config_qosmac_del(0x43ef30)`；该函数在 `0x43ef8c` 读取缺失字段 `select_editnum_mac`，并在 `0x43efb0` 对空指针执行 `lb`，最终崩溃

- Main地址: `0x408120`

- 子进程trace链: 未使用；入口 trace 已足够闭合调用链
- 关键pc地址:
  - `0x40a6c0`: `sym.post_apply`
  - `0x40aa18`: 调用 `sym.cgi_setobject`
  - `0x40f7ec`: 从动作表取出已匹配项的函数指针
  - `0x40f808`: `jalr t9` 跳转到具体 handler
  - `0x43ef30`: `sym.config_qosmac_del`
  - `0x43ef8c`: `cgi_value("select_editnum_mac", ...)`
  - `0x43efb0`: `lb v1, (s2)`，实际 faulting sink

## 数据流细节

- 哪些数据包字段控制了哪些变量:
  - `body.submit_flag="qos_delmac"` 控制 `sym.cgi_setobject` 的分发表匹配结果，决定调用 `sym.config_qosmac_del`
  - `body.select_editnum_mac` 本应提供待删除 MAC 项编号；本次请求中该字段缺失，因此 `cgi_value` 返回空指针
  - 其余字段如 `wan_ether_dns1`、`wan_ether_dns2`、`%20timestamp`、`upgrade_yes_no` 未出现在崩溃路径的关键取值点
- 哪个函数读取了source字段:
  - `sym.config_qosmac_del` 在 `0x43ef8c` 调用 `cgi_value("select_editnum_mac", req_ctx, aux)` 读取 source 字段
- 哪个函数写入 / 拼接 / 格式化了攻击者可控数据:
  - 无复杂拼接；`cgi_value` 直接把请求字段值或 `NULL` 返回给调用者，`0x43ef88` 将返回值保存到 `s2`
- 最终如何到达sink:
  - `submit_flag` 先把控制流导向 `sym.config_qosmac_del`
  - `cgi_value("select_editnum_mac")` 返回 `NULL`
  - `0x43efb0` 对 `s2` 执行 `lb v1, (s2)`，即对 `NULL` 地址读 1 字节
  - `trace/entry_trace.txt` 在 `pc=0x43efac` 后立即出现 `--- SIGSEGV {si_addr=NULL} ---`，与该解引用一致

## 误报检查

- 为什么这是一个真实漏洞，或者为什么它更像误报:
  - 这是一个真实漏洞。崩溃不是环境噪声，也不是通用模拟异常；调用链、字段选择、handler 跳转和空指针 sink 都能由 `entry_trace`、反汇编和容器日志相互印证。
- 当前缺失的证据:
  - 没有运行时寄存器转储直接显示 `s2==0`，但 `si_addr=NULL` 与 `0x43efb0` 的 `lb v1,(s2)` 已足以闭合证据链。
- 对当前现象的替代解释:
  - 最合理的替代解释是 `cgi_value("select_editnum_mac")` 返回了悬空指针而非 `NULL`；但这与 `si_addr=NULL` 不符，因此不成立。
