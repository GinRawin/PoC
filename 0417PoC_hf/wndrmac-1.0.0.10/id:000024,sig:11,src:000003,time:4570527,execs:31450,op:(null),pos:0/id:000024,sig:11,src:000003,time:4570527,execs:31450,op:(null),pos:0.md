## 摘要

- 判定: `确认漏洞`
- Sink位置: `/usr/sbin/uhttpd fcn.0043e314 0x43e368 (call sym.imp.atoi)`
- Source位置: `/usr/sbin/uhttpd fcn.0043e314 0x43e358 (call sym.cgi_value("select_editnum_mac"))`
- 漏洞二进制: `/usr/sbin/uhttpd`
- 漏洞类型: `NULL pointer dereference / 缺失参数校验`
- 一句话根因: `config_edit_qos_mac` 路径下，代码对 CGI 字段 `select_editnum_mac` 的返回值未做 NULL 检查，直接传给 `atoi`，当请求中省略该字段时触发 `SIGSEGV`
- 数据包字段 -> 变量赋值:
  - `body.submit_flag = "edit_qos_mac"` -> `s1/v0` in `cgi_setobject` / `cgi_func`，用于匹配分发表并进入 `sym.config_edit_qos_mac (0x43ebb0)`
  - `body.select_editnum_mac` `缺失` -> `v0 = NULL` at `sym.cgi_value` return `0x40e3cc` -> `a0 = v0` at `0x43e36c` -> `atoi(a0)` at `0x43e368`
- 执行顺序:
  1. `POST /apply.cgi?` 进入 `uhttpd` 的通用 CGI 分发路径，`cgi_setobject` 在 `0x40f7b0` 读取 `submit_flag`
  2. `submit_flag=edit_qos_mac` 使控制流命中 `sym.config_edit_qos_mac (0x43ebb0)`，而不是 `request.handler_name` 里的 `passphrase_bg_msg`
  3. `sym.config_edit_qos_mac` 调用 `fcn.0043e314`，其中 `0x43e358` 读取 `select_editnum_mac`，`sym.cgi_value` 在 `0x40e3cc` 返回 `NULL`
  4. `fcn.0043e314` 在 `0x43e368` 调用 `atoi(NULL)`，trace 落到 `0x43e360 -> 0x44b690` 后以 `SIGSEGV si_addr=NULL` 结束

## 误报检查

- 为什么这是一个真实漏洞，或者为什么它更像误报:
  - 这是一个真实漏洞。容器日志和 trace 都显示实际 `SIGSEGV`，且崩溃前最后一条可解释的数据流是 `cgi_value("select_editnum_mac") -> NULL -> atoi(NULL)`，根因和 fault site 均已落到真实指令
- 当前缺失的证据:
  - 无关键缺失证据；若需要更强佐证，只能再补 CGI 参数表的运行时内存快照，但当前 trace 与反汇编已足够确认
- 对当前现象的替代解释:
  - 替代解释 1: 超长的 `upgrade_yes_no` 或 `%20timestamp` 内容导致了内存破坏。该解释不成立，因为崩溃前关键路径没有消费这些字段，且 `check_timestamp` 直接返回 0
  - 替代解释 2: 真正命中的是 `passphrase_bg_msg` handler。该解释也不成立，因为尾部 trace 明确进入的是 `config_edit_qos_mac (0x43ebb0)`，命中条件来自 `submit_flag=edit_qos_mac`
