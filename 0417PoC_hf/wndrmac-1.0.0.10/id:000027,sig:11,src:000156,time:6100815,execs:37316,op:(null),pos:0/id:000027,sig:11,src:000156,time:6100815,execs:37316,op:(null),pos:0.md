# 漏洞分析: wndrmac-1.0.0.10 / id:000027,sig:11,src:000156,time:6100815,execs:37316,op:(null),pos:0

## 摘要

- 判定: `确认漏洞`
- Sink位置: `usr/sbin/uhttpd sym.config_USB_advanced 0x430920`
- Source位置: `VulPacket.json body.hidden_is_ftp (缺失); usr/sbin/uhttpd sym.config_USB_advanced 0x430914`
- 漏洞二进制: `usr/sbin/uhttpd`
- 漏洞类型: `NULL pointer dereference / DoS`
- 一句话根因: `config_USB_advanced()` 在调用 `cgi_value("hidden_is_ftp", ...)` 后没有检查返回值是否为 NULL，就在 `0x430920` 直接解引用，导致缺失该字段的请求可触发 SIGSEGV。`
- 数据包字段 -> 变量赋值:
  - `request.handler_name=apply.cgi?/USB_Folder_edit.htm?editFolderID=` -> 命中 `apply.cgi` CGI 处理路径
  - `body.submit_flag="USB_advanced"` -> `sym.cgi_setobject` 中 `cgi_value("submit_flag")` 的返回值 `s1/v0`，用于匹配 `obj.funcs` 表项 `{0x44df14 "USB_advanced", 0x1a, 0x4308b8}`
  - `body.hidden_is_ftp` 缺失 -> `sym.config_USB_advanced` 中 `cgi_value("hidden_is_ftp")` 的返回值 `v0=NULL`
  - `body.wan_pppoe_intranet_ip`、`body["%20timestamp"]` -> 未见流入本次崩溃 sink，只是请求中的无关字段
- 执行顺序:
  1. `POST /apply.cgi?/USB_Folder_edit.htm?editFolderID=` 被解析成 CGI 键值对后，`sym.cgi_setobject` 在 `0x40f7b4` 调用 `cgi_value("submit_flag", ...)` 取出 `submit_flag`
  2. `sym.cgi_setobject` 在 `0x40f838`/`0x40f848` 用 `strcmp` 将该值与 `obj.funcs` 表中的名字逐项比较，并在匹配 `"USB_advanced"` 后通过表项中的函数指针 `0x4308b8` 跳入 `sym.config_USB_advanced`
  3. `sym.config_USB_advanced` 在 `0x430914` 调用 `cgi_value("hidden_is_ftp", ...)`，本次请求缺失该字段导致返回 `NULL`，随后 `0x430920: lb v1, 0(v0)` 对 NULL 解引用并触发 `SIGSEGV`

## 数据流细节

- 哪些数据包字段控制了哪些变量:
  - `request.handler_name` 决定进入 `apply.cgi` 处理路径
  - `body.submit_flag="USB_advanced"` 控制 `sym.cgi_setobject` 选中 `obj.funcs` 中的 `"USB_advanced"` 项，并把控制流导向 `sym.config_USB_advanced`
  - `body.hidden_is_ftp` 本应提供给 `sym.config_USB_advanced`；本次请求中该字段缺失，因此对应查找结果为 `NULL`
- 哪个函数读取了source字段:
  - `sym.cgi_value` 负责在 CGI 参数数组中查找指定键。`sym.config_USB_advanced` 在 `0x430910`/`0x430914` 以字符串常量 `"hidden_is_ftp"` 调用该函数
- 哪个函数写入 / 拼接 / 格式化了攻击者可控数据:
  - 本次崩溃不依赖字符串拼接或格式化；`sym.cgi_value` 直接在已解析的 CGI 键值对数组中做键名匹配，未命中即返回 `NULL`
- 最终如何到达sink:
  - `VulPacket.json` 里的 `body.submit_flag="USB_advanced"` -> `sym.cgi_setobject` 的 `s1/v0`
  - `s1` 与 `obj.funcs` 表项 `"USB_advanced"` 匹配 -> 函数指针 `0x4308b8`
  - `sym.config_USB_advanced` 调用 `cgi_value("hidden_is_ftp", parsed_pairs, pair_count)` -> `v0=NULL`
  - `0x430920` 直接执行 `lb v1, 0(v0)` -> NULL dereference -> `SIGSEGV`

## 误报检查

- 为什么这是一个真实漏洞，或者为什么它更像误报:
  - 崩溃由二进制内可解释的空指针解引用直接触发，而不是模糊测试噪声。trace 已显示程序从 `sym.config_USB_advanced` 调用 `cgi_value("hidden_is_ftp")` 返回后立即异常；反汇编明确表明下一条关键内存访问是 `0x430920: lb v1, 0(v0)`，且 `trace`/`console` 都给出 `si_addr=NULL`
  - 请求中存在合法的路径和 `submit_flag=USB_advanced`，说明攻击者可以稳定到达该代码路径；仅通过省略 `hidden_is_ftp` 即可触发
- 当前缺失的证据:
  - 无关键缺失证据；虽然没有寄存器转储，但 `trace + 反汇编 + SIGSEGV(NULL)` 已足以闭合根因
- 对当前现象的替代解释:
  - 更弱的替代解释是 `cgi_value` 内部比较过程中发生了崩溃，但这与 trace 不符：`0x40e3cc` 显示 `cgi_value` 已走到返回 `0` 的路径，随后控制流回到 `0x43091c`，因此真正 fault site 不是 `strcmp`，而是返回后对 `v0` 的未检查解引用
