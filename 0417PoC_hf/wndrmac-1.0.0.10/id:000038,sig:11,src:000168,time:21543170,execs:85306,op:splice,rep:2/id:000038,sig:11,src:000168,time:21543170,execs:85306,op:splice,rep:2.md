# 漏洞分析: wndrmac-1.0.0.10 / id:000038,sig:11,src:000168,time:21543170,execs:85306,op:splice,rep:2

## 摘要

- 判定: `确认漏洞`
- Sink位置: `/usr/sbin/uhttpd` `sym.config_add_qos_mac` `0x0043eb58` (`strcmp`)
- Source位置: `/usr/sbin/uhttpd` `sym.cgi_value` `0x0040e3cc` (`body.wds_mac` 缺失后返回 `NULL`)
- 漏洞二进制: `/usr/sbin/uhttpd`
- 漏洞类型: `NULL pointer dereference`
- 一句话根因: `config_add_qos_mac` 从 CGI 表中取 `wds_mac` 后未做空指针检查，直接把 `cgi_value("wds_mac", ...)` 的返回值送入 `strcmp`，当请求中缺失该字段时触发崩溃。
- 数据包字段 -> 变量赋值:
  - `body.submit_flag="add_qos_mac"` -> `sym.cgi_setobject` 中 `s1=v0`，命中 `config_add_qos_mac`
  - `body.wds_mac` 缺失 -> `sym.cgi_value` 返回 `v0=0`，随后在 `sym.config_add_qos_mac` 中被移动到 `a0`
- 执行顺序:
  1. `POST /apply.cgi?` 请求进入 `uhttpd`，`submit_flag=add_qos_mac` 被 `sym.cgi_setobject` 读取并映射到 `config_add_qos_mac`
  2. `sym.config_add_qos_mac` 调用 `cgi_value("wds_mac", ...)`，本次 trace 显示其走到 `0x40e3cc` 返回 `NULL`
  3. 返回值未经校验即在 `0x43eb58` 作为 `strcmp` 第一个参数使用，随后出现 `SIGSEGV`

## 误报检查

- 为什么这是一个真实漏洞，或者为什么它更像误报:
  - 这是一个真实漏洞。崩溃信号、trace 执行顺序、反汇编三者一致，且可以解释完整控制流和数据流: `submit_flag` 负责命中 handler，`wds_mac` 缺失导致 `NULL` 传播到 `strcmp`
- 当前缺失的证据:
  - 没有寄存器转储直接显示 `a0==NULL`；但 `trace/usr_sbin_uhttpd.txt` 已显示 `cgi_value` 走到 `0x40e3cc` 返回空值，且返回后立即进入 `strcmp` 路径，证据已足够定性
- 对当前现象的替代解释:
  - 替代解释只能是仿真器在 `0x43eb4c` 附近记录 PC 略有偏移；但这不会改变根因，因为唯一紧邻的危险调用就是 `strcmp(v0, "1")`
