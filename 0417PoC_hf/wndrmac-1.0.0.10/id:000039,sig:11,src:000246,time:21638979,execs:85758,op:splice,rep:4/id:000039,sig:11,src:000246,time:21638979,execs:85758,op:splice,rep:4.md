# 漏洞分析: wndrmac-1.0.0.10 / id:000039,sig:11,src:000246,time:21638979,execs:85758,op:splice,rep:4

## 摘要

- 判定: `确认漏洞`
- Sink位置: `/usr/sbin/uhttpd config_remote@0x4410dc strcmp调用点@0x441248`
- Source位置: `/usr/sbin/uhttpd config_remote@0x44121c cgi_value("remote_management") -> cgi_value@0x40e3cc(return NULL)`
- 漏洞二进制: `/usr/sbin/uhttpd`
- 漏洞类型: `NULL pointer dereference / 拒绝服务`
- 一句话根因: `config_remote()` 对 `cgi_value("remote_management")` 的返回值缺少 NULL 检查，直接把缺失字段对应的 NULL 指针传给 `strcmp()`，导致 SIGSEGV。
- 数据包字段 -> 变量赋值:
  - `request.prefix="/apply.cgi?"` -> 进入 `uhttpd` 的 CGI 配置提交流程
  - `body.submit_flag="remote"` -> `cgi_setobject@0x40f754` 中 `s1=v0`，匹配 `funcs[21]="remote"`，分发到 `config_remote@0x4410dc`
  - `body.remote_management` 缺失 -> `config_remote@0x44121c` 调用 `cgi_value("remote_management", s2, s3)` 返回 `v0=0`，随后 `s0=v0`
- 执行顺序:
  1. POST `/apply.cgi?` 的参数表中 `submit_flag=remote` 被 `cgi_setobject()` 读出，并在 `funcs` 分发表中命中 `remote -> config_remote@0x4410dc`。
  2. `config_remote()` 先尝试读取 `http_rmport` 和 `http_rmenable`，二者缺失时直接跳到 `remote_management` 分支；随后 `cgi_value("remote_management")` 因缺字段返回 `NULL`。
  3. `config_remote()` 将该 NULL 赋给 `s0`，并在 `0x441248` 调用 `strcmp(s0, "ip_single")`，最终触发空指针解引用并崩溃。

## 数据流细节

- 哪些数据包字段控制了哪些变量:
  - `body.submit_flag="remote"` 控制 `cgi_setobject()` 的分发表选择，保证控制流进入 `config_remote()`。
  - `body.remote_management` 缺失，导致 `config_remote()` 内对该键的查找结果为 NULL；这是直接流入 sink 的关键输入条件。
  - `body.http_rmport` 和 `body.http_rmenable` 同样缺失，但这里只影响前半段配置逻辑是否跳过，不是崩溃必要条件。
- 哪个函数读取了source字段:
  - `cgi_setobject@0x40f754` 通过 `cgi_value("submit_flag", s3, s4)` 读取 `submit_flag`。
  - `config_remote@0x44121c` 通过 `cgi_value("remote_management", s2, s3)` 读取 `remote_management`。
- 哪个函数写入 / 拼接 / 格式化了攻击者可控数据:
  - 本案没有额外拼接或格式化；`cgi_value()` 直接返回参数表中的 value 指针，或者在未命中时于 `0x40e3cc` 直接返回 `0`。
- 最终如何到达sink:
  - `body.submit_flag="remote"` -> `cgi_setobject:s1` -> `funcs[21]={"remote",2,0x4410dc}` -> `config_remote(s3,s4)`
  - `body.remote_management` 缺失 -> `cgi_value("remote_management", s2, s3)` 返回 `v0=0`
  - `0x44123c` 将 `v0` 保存到 `s0`
  - `0x441240`/`0x441248` 以 `a0=s0(NULL)`、`a1="ip_single"` 调用 `strcmp`
  - `strcmp` 对 NULL 解引用，`trace/entry_trace.txt` 末尾以 `SIGSEGV ... si_addr=NULL` 结束

## 误报检查

- 为什么这是一个真实漏洞，或者为什么它更像误报:
  - 这是一个真实漏洞。崩溃日志、入口 trace、分发表、`cgi_value()` 的返回路径和 `strcmp()` 调用点可以闭合成完整链条，而且真实危险实参是 `cgi_value("remote_management")` 返回的 NULL，不是模糊的“崩溃地址附近猜测”。
- 当前缺失的证据:
  - 没有源码级变量名和 C 行号；但汇编、符号表、字符串常量和 trace 已足以确认 source、变量和 sink。
- 对当前现象的替代解释:
  - 最合理的替代解释是“请求整体未被正常解析，导致所有参数都缺失”。但这与事实不符，因为 `submit_flag=remote` 已被成功读出并命中 `funcs[21]`，说明参数表存在且控制流确实进入了 `config_remote()`。崩溃不是由畸形 `handler_name`、header 值或其他随机字段触发，而是由缺失的 `remote_management` 字段触发的空指针比较。
