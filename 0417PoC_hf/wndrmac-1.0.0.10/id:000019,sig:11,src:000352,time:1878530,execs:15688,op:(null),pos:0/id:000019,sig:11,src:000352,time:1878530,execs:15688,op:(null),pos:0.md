# 漏洞分析: wndrmac-1.0.0.10 / id:000019,sig:11,src:000352,time:1878530,execs:15688,op:(null),pos:0

## 摘要

- 判定: `确认漏洞`
- Sink位置: `/usr/sbin/uhttpd sym.do_apply 0x40aa78`
- Source位置: `/usr/sbin/uhttpd sym.cgi_setobject 0x40f7a4`
- 漏洞二进制: `/usr/sbin/uhttpd`
- 漏洞类型: `NULL` 指针解引用
- 一句话根因: `submit_flag` 被读入后未命中任何 `obj.funcs` 动作项，导致全局 `obj.cgi_action` 保持全零，`cgi_setobject` 跳过唯一一次 `obj.refresh_time` 初始化，随后 `do_apply` 解引用了仍为 `NULL` 的 `*obj.refresh_time`。
- 数据包字段 -> 变量赋值:
  - `body.submit_flag` -> `s1`（`cgi_value("submit_flag", ...)` 返回值） -> `strcmp(obj.funcs[i].name, s1)` 比较输入
  - `body.submit_flag` -> `obj.cgi_action` 保持零值状态（未命中 `0x40f7ec` 设置块）
  - `request.prefix + request.handler_name` -> `handle_request` 命中 `/apply.cgi` 处理逻辑 -> 调用 `do_apply`
  - `obj.cgi_action == 0` -> `obj.refresh_time` 未在 `0x40f9d8` 写入 -> `do_apply` 在 `0x40aa78` 解引用 `NULL`
- 执行顺序:
  1. `POST /apply.cgi` 进入 `post_apply`，`cgi_setobject` 在 `0x40f7a4` 读取 `body.submit_flag`。
  2. `cgi_setobject` 先清零 `obj.cgi_action`，随后在 `0x40f830..0x40f848` 用 `submit_flag` 遍历比较动作表；trace 只出现循环块，未出现命中块 `0x40f7ec`，因此 `obj.cgi_action` 保持全零。
  3. `handle_request` 早先已把 `*obj.refresh_time` 清零；本次 `cgi_setobject` 又在 `0x40f9c8` 直接跳到 `0x40f9e4`，跳过 `0x40f9d8` 唯一写入点。
  4. `handle_request` 最终调用 `do_apply`；`do_apply` 在 `0x40aa78` 对 `*obj.refresh_time` 做解引用，触发 `SIGSEGV si_addr=NULL`。

## 数据流细节

- 哪些数据包字段控制了哪些变量:
  - `body.submit_flag` 控制 `cgi_setobject` 中的 `s1`，并作为 `strcmp` 的第二实参参与动作匹配。
  - `request.prefix="/"` 与 `request.handler_name="apply.cgi"` 控制 `handle_request` 落入 `apply.cgi` 分支，并最终调用 `do_apply`。
  - `body.%20timestamp` 没有被证实流入 sink；当前二进制在 `handle_request` 早期查找的是 URI 中的 `&20timestamp=`，不是这里的 POST body 键。
- 哪个函数读取了source字段:
  - `sym.cgi_setobject` 在 `0x40f7a4..0x40f7b8` 调用 `cgi_value("submit_flag", parsed_table, count)` 读取 `body.submit_flag`。
- 哪个函数写入 / 拼接 / 格式化了攻击者可控数据:
  - `sym.cgi_setobject` 在 `0x40f830..0x40f848` 将 `submit_flag` 作为 `strcmp` 的比较对象逐项和 `obj.funcs[i].name` 比较；因为没有命中，原本应在 `0x40f7ec..0x40f810` 设置的 `obj.cgi_action` 字段没有被写入。
- 最终如何到达sink:
  - `sym.handle_request` 在 `0x40cf7c..0x40cf80` 先把 `*obj.refresh_time` 清零。
  - `sym.cgi_setobject` 开头在 `0x40f794..0x40f79c` 清零 `obj.cgi_action`，trace 显示后续只走了比较循环 `0x40f830/0x40f83c/0x40f848/0x40f850`，没有进入命中块 `0x40f7ec`，因此 `obj.cgi_action` 保持全零。
  - 之后 `0x40f858..0x40f9c8` 读取 `obj.cgi_action` 的多个标志位；这些位全为 0，使执行流直接从 `0x40f9c8` 跳到 `0x40f9e4`，跳过唯一的 `obj.refresh_time` 写入点 `0x40f9d8..0x40f9dc`。
  - `sym.do_apply` 在 `0x40aa6c` 取到 `obj.refresh_time` 的全局槽地址，在 `0x40aa78` 执行 `lw v0, (v0)` 时解引用了仍为 `NULL` 的 `*obj.refresh_time`，触发崩溃。

## 误报检查

- 为什么这是一个真实漏洞，或者为什么它更像误报:
  - 这是一个真实漏洞。容器日志和入口 trace 都确认了 `SIGSEGV`，并且静态控制流能够解释为什么 `*obj.refresh_time` 在本次请求中保持 `NULL`。崩溃不是外部环境噪声，也不是单纯的日志异常。
- 当前缺失的证据:
  - 没有寄存器级 trace 直接打印 `0x40aa78` 当下的 `v0`，但当前 trace 顺序、`si_addr=NULL`、以及 `refresh_time` 初始化块被跳过的反汇编证据已经足以闭合根因链。
- 对当前现象的替代解释:
  - 初看也可以把崩溃解释为 `0x40aa88` 的 `strstr(NULL, "BRS_")`。但 `handle_request` 中 `0x2730(sp)` 的初始化和传递路径表明传入 `do_apply` 的 URI/查询指针并不会在这条路径上变成 `NULL`；相比之下，`refresh_time` 被清零且写回块未执行，和 `si_addr=NULL` 更一致。
