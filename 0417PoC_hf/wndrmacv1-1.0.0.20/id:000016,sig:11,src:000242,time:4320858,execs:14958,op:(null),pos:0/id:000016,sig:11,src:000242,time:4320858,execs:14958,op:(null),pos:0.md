## 摘要

- 判定: `确认漏洞`
- Sink位置: `uhttpd 0x40afd4 0x40b7f4`（`a0=s6`，对 `"routerlogin.net"` 的 `strstr` 风格字符串搜索调用；同路径还有 `0x40b810` 对 `"routerlogin.com"` 的第二次调用）
- Source位置: `uhttpd 0x40afd4 0x40b4dc`（`Host:` 头解析分支；本样本未提供该字段，导致 `s6` 保持 `0x40b030` 初始化的 `NULL`）
- 漏洞二进制: `/usr/sbin/uhttpd`
- 漏洞类型: `NULL pointer dereference` / 远程拒绝服务
- 一句话根因: 请求未携带 `Host` 头时，`uhttpd` 在请求解析阶段让主机名指针 `s6` 保持为 `NULL`，但在后续 `dns_hijack` 路径里仍把该空指针传给字符串搜索函数与 `routerlogin.net/com` 比较，最终触发 `SIGSEGV`
- 数据包字段 -> 变量赋值:
  - `header.Host` 缺失 -> `s6 == NULL`（`0x40b030` 清零初始化后，`0x40b4dc-0x40b578` 的 `Host:` 解析分支未命中）
  - `request.prefix="/"` -> `[sp+0x2730]` 中的 URI 仍为 `/`，使 `0x40b6cc` 对 `"/shares"` 的比较返回非零，继续进入 `0x40b7c8` 的 host 检查分支
- 执行顺序:
  1. `0x40afd4` 开始的请求解析函数把整条 HTTP 请求拆成 method / URI / version / headers，并先在 `0x40b030` 把 `s6` 初始化为 `NULL`
  2. 样本只带了 `Content-Type`，没有 `Host`，因此 `0x40b4dc-0x40b578` 的 `Host:` 解析逻辑不执行，`s6` 一直保持空指针；随后 `request.prefix="/"` 使 `0x40b6cc` 的 `"/shares"` 比较失败，落入 `0x40b7c8`
  3. `0x40b7f4` 将 `s6` 作为第一个实参传入对 `"routerlogin.net"` 的字符串搜索调用，空指针在该 sink 内被解引用并导致 `SIGSEGV`

- 哪些数据包字段控制了哪些变量:

  - `request.prefix="/"` 控制 URI 缓冲区 `[sp+0x2730]` 的内容，使 `0x40b6bc-0x40b6d4` 对 `"/shares"` 的比较为不相等，从而走到后续 host 检查

- 哪个函数读取了source字段:
  - `uhttpd` 内部请求解析函数（起始地址 `0x40afd4`）逐行扫描 header
  - 在 `0x40b4dc` 处用长度为 5 的前缀比较匹配 `"Host:"`，若命中则在 `0x40b4fc-0x40b578` 去掉空白并把值地址写入 `s6`
- 哪个函数写入 / 拼接 / 格式化了攻击者可控数据:
  - 同一个解析函数先把原始请求拷贝到栈上缓冲区（`0x40b010-0x40b028`），随后直接在该缓冲区内原地插入 `NUL` 分隔符
  - `Host` 不会被重新格式化；若存在则 `s6` 直接指向请求缓冲区中的 Host 值。此次因为字段缺失，真正流向 sink 的是“未被赋值的空指针状态”
- 最终如何到达sink:
  - `0x40b030`: `s6 = 0`
  - `0x40b4dc-0x40b578`: 仅当 header 行以 `"Host:"` 开头时才会执行 `s6 = host_value_ptr`
  - `0x40b6a4`: 把 `s6` 传给 `http_access_type(0x418b04)`；该函数在 `0x418b48` 明确处理 `a0 == NULL`
  - `0x40b6bc-0x40b6d4`: URI 不是 `"/shares"`，进入 `0x40b7c8`
  - `0x40b7f4`: 再次把同一个 `s6` 传给对 `"routerlogin.net"` 的 `strstr` 风格调用
  - `0x40b810`: 若第一条未命中，还会对 `"routerlogin.com"` 做第二次同类调用
  - 因为 `s6 == NULL`，第一次调用已在库函数内部崩溃

## 误报检查

- 为什么这是一个真实漏洞，或者为什么它更像误报:
  - 这是可复现的真实漏洞。`container.console.log` 与 `trace/usr_sbin_uhttpd.txt` 同时给出 `SIGSEGV`，且反汇编能解释出完整的“缺失 `Host` -> `s6 == NULL` -> 进入 host 检查 -> 字符串搜索解引用空指针”链条
  - `0x418b04 (http_access_type)` 的执行轨迹经过 `0x418b48`，直接证明传入它的 `a0` 为 `NULL`；这与样本缺失 `Host` 头严格吻合
  - 崩溃点不是机械地等于根因。根因是 `0x40b7f4`/`0x40b810` 在 `dns_hijack` 路径下复用了未校验的空 `Host` 指针
- 当前缺失的证据:
  - 没有可直接打印 GOT 解析结果的重定位表，所以 `0x40b7f4` 处导入函数名无法通过重定位条目逐字确认；这里只能根据调用语义和字符串字面量判断为 `strstr` 风格搜索
- 对当前现象的替代解释:
  - 更弱的替代解释是“某处栈或 `gp` 被破坏后偶然在比较 host 时崩溃”。但这与 `0x418b48` 明确展示的 `a0 == NULL` 不一致，也无法解释为何样本刚好缺失 `Host` 头。因此当前最合理解释仍是缺失 `Host` 触发的空指针解引用
