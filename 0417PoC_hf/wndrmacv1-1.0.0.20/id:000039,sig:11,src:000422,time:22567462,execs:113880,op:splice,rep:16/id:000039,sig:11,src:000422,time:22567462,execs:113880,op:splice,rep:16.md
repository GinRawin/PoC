# 漏洞分析: wndrmacv1-1.0.0.20 / id:000039,sig:11,src:000422,time:22567462,execs:113880,op:splice,rep:16

## 摘要

- 判定: `确认漏洞`
- Sink位置: `/usr/sbin/uhttpd` `sub_432dc0` `0x432e9c -> 0x445880(atoi)`
- Source位置: `/usr/sbin/uhttpd` `cgi_value` `0x40cf50 / 0x40cf70`
- 漏洞二进制: `/usr/sbin/uhttpd`
- 漏洞类型: `NULL pointer dereference`
- 一句话根因: `sub_432dc0` 在 `pppoe`/WAN 配置分支中读取 CGI 参数 `igmp_value` 后，未检查 `cgi_value()` 的返回值是否为 `NULL`，直接调用 `atoi(NULL)`，导致 `SIGSEGV`。
- 数据包字段 -> 变量赋值:
  - `body.igmp_value`(本次请求中缺失) -> `s1 = cgi_value("igmp_value", s3, s4)`，返回 `NULL`
  - `request.prefix = "/apply.cgi?"` -> 命中 CGI 处理路径
  - `body.submit_flag = "wan"` -> 命中 WAN 配置分支
- 执行顺序:
  1. `POST /apply.cgi?` 请求进入 `uhttpd`，trace 落到 `0x432dc0` 对应的 WAN/`pppoe` 配置处理逻辑。
  2. `0x432e64` 通过 `cgi_value("igmp_value", s3, s4)` 从 CGI 参数表取值，返回值保存在 `s1`。
  3. 由于本次请求未提供 `igmp_value`，`s1 == NULL`，随后 `0x432ea0` 调用 `atoi(s1)`，在 `0x445880` 导入桩进入 `atoi(NULL)` 后崩溃。

## 数据流细节

- 哪些数据包字段控制了哪些变量:
  - `request.prefix = "/apply.cgi?"` 决定请求走 CGI 处理入口。
  - `body.submit_flag = "wan"` 使请求进入 WAN 设置逻辑；`0x100004dc` 的函数表项表明 `0x432dc0` 是 WAN 类型表中的 `pppoe` 处理函数。
  - `body.igmp_value` 是本函数期待读取的真实 source 字段；本次包中该字段缺失，因此 `cgi_value("igmp_value", ...)` 返回 `NULL`。
- 哪个函数读取了source字段:
  - `cgi_value` (`0x40cf10`) 遍历 CGI `name/value` 数组。`0x40cf50` 读取当前条目的键，匹配后在 `0x40cf70` 返回对应的值指针；未命中则在 `0x40cf7c` 返回 `0`。
- 哪个函数写入 / 拼接 / 格式化了攻击者可控数据:
  - 本次崩溃不依赖复杂拼接；攻击面是 HTTP 请求体被解析成 CGI 参数表后，`cgi_value` 直接从该表返回用户提供值或 `NULL`。更早的解析写入点在当前允许输入中不可见，但不影响 sink 处实参核验。
- 最终如何到达sink:
  - `sub_432dc0` 在 `0x432e54` 调用 `cgi_value("igmp_value", s3, s4)`，返回值写入 `s1`。
  - 本次 trace 显示该调用后直接走到 `0x40cf7c`，说明 `cgi_value` 未找到该参数并返回 `0`。
  - `0x432e98` 把 `s1` 送入 `$a0`，`0x432ea0` 通过 GOT 表项 `0x10003c94` 调用导入函数 `0x445880`；该 GOT 符号解析为 `atoi`。
  - `atoi(NULL)` 触发空指针解引用，entry trace 末尾记录为 `0x445880 -> 0x432e94 -> SIGSEGV`，容器日志也记录 `SIGSEGV CAUGHT`。

## 误报检查

- 为什么这是一个真实漏洞，或者为什么它更像误报:
  - 崩溃点、危险实参和请求字段之间的链条是闭合的：`cgi_value("igmp_value") -> NULL -> atoi(NULL)`。这里不是模糊的“异常退出”，而是可定位到真实 sink 的空指针解引用。
- 当前缺失的证据:
  - CGI 参数表更早的构造函数没有在当前允许输入里直接展开，所以无法给出“HTTP body 解析函数”的精确地址。
- 对当前现象的替代解释:
  - 最合理的替代解释是“请求缺少必填字段导致业务错误”，但该解释不足以推翻漏洞结论，因为程序没有做空值校验，最终在 `atoi(NULL)` 处发生了真实进程崩溃。
