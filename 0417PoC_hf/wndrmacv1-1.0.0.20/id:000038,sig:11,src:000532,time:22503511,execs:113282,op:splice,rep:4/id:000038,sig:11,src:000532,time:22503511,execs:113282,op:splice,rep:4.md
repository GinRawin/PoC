# 漏洞分析: wndrmacv1-1.0.0.20 / id:000038,sig:11,src:000532,time:22503511,execs:113282,op:splice,rep:4

## 摘要

- 判定: `确认漏洞`
- Sink位置: `/usr/sbin/uhttpd fcn.004086c4 0x00408730 (jalr sym.imp.sprintf)`
- Source位置: `/usr/sbin/uhttpd sym.handle_request 0x0040c3f8`
- 漏洞二进制: `/usr/sbin/uhttpd`
- 漏洞类型: 栈缓冲区溢出 / 返回地址覆盖
- 一句话根因: `handle_request` 将来自 HTTP 请求路径的用户可控字符串直接传给 `fcn.004086c4`，后者在 `0x408714-0x408730` 用 `sprintf` 将其拼接到栈缓冲区 `sp+0x20`，没有长度检查，导致覆盖保存的 `ra`，最终在 `sym.do_file` 返回时跳转到伪造地址 `0x61616160` 并触发 `SIGSEGV`。
- 数据包字段 -> 变量赋值:
  - `request.prefix` + `request.handler_name` -> HTTP request line 中的 URI/path -> `sym.handle_request` 的 `s3` -> `fcn.004086c4` 的 `a2/s3`
- 执行顺序:
  1. `uhttpd` 读取请求行并在 `sym.handle_request` 中解析 URI，后续把路径指针恢复到 `s3`。
  2. `sym.handle_request` 在 `0x40c3f8` 将该路径指针作为实参传入 `fcn.004086c4`。
  3. `fcn.004086c4` 在 `0x408714-0x408730` 对栈缓冲区执行 `sprintf`，覆盖返回地址；稍后进入 `sym.do_file`，在 `0x408a94` 附近退栈返回时转去 `0x61616160` 并崩溃。

  - `0x408a94` 后触发 `SIGSEGV`, `si_addr=0x61616160`

## 数据流细节

- 哪些数据包字段控制了哪些变量:
  - `request.prefix` 与超长 `request.handler_name` 一起组成请求 URI。
  - 该 URI 经 `handle_request` 的请求行解析后，路径指针被恢复到栈槽 `sp+0x2730`，并在 `0x40c3b8` 加载到 `s3`。
- 哪个函数读取了source字段:
  - `sym.handle_request` 在 `0x40b010` 先 `fgets` 读取请求行到栈缓冲区，再通过多次 `strsep` 解析；后续在 `0x40c3b8/0x40c3f8` 使用该路径指针。
- 哪个函数写入 / 拼接 / 格式化了攻击者可控数据:
  - `fcn.004086c4` 在 `0x408714-0x408730` 执行 `sprintf(sp+0x20, ..., s3, s2)`。其中目标缓冲区位于当前栈帧 `sp+0x20`，而保存的寄存器区直到 `sp+0xa0/sp+0xb0`，超长路径足以覆盖保存的 `s0/s1/s2/s3/ra`。
- 最终如何到达sink:
  - `request.handler_name` 中的大量 `a` 进入 URI path
  - URI path -> `sym.handle_request` 的 `s3`
  - `s3` -> `fcn.004086c4` 的 `a2/s3`
  - `sprintf` 写入 `sp+0x20`
  - 覆盖返回地址
  - `sym.do_file` 在 `0x408a94` 退栈返回时使用被污染的 `ra`
  - 跳转到 `0x61616160`，崩溃

## 误报检查

- 为什么这是一个真实漏洞，或者为什么它更像误报:
  - 这不是单纯的“文件不存在”或 `fopen` 空指针误用。`sym.do_file` 在 `0x4089f0` 明确对 `fopen` 返回值做了空指针检查，若文件打不开会直接走 `0x408a94` 的正常返回路径。真正异常的是返回地址已被攻击者数据破坏，导致函数返回时跳到 `0x61616160`。
- 当前缺失的证据:
  - 没有寄存器转储，无法逐字节展示被覆盖后的 `ra` 栈内容。
- 对当前现象的替代解释:
  - 最合理的替代解释是“某个更早的栈写越界破坏了 `ra`，`0x408a94` 只是暴露点”。而现有反汇编和 trace 指向最直接、最可信的越界点就是 `fcn.004086c4` 的无界 `sprintf`。
