# 漏洞分析: wndrmacv1-1.0.0.20 / id:000007,shmid:11,addr:0x7,4253752

## 摘要

- 判定: `确认漏洞`
- Sink位置: `uhttpd sym.cmd_wifi_coexist@0x004124d0 0x004124dc`
- Source位置: `uhttpd callback@0x0040dd64 0x0040de14`
- 漏洞二进制: `/usr/sbin/uhttpd`
- 漏洞类型: `NULL pointer dereference / DoS`
- 一句话根因: `submit_flag=wifi_channel_coexist` 会把 `cgi_action[0x32]` 置 1 并进入 `cmd_wifi_coexist`，但对应参数字段 `hidd_coexist_flag` 缺失时，`cgi_value("hidd_coexist_flag")` 返回 NULL，导致全局参数 `0x1000d080` 未初始化，最终以 `a0=NULL` 调用并在 `lb v0,(a0)` 崩溃。
- 数据包字段 -> 变量赋值:
  - `body.submit_flag = "wifi_channel_coexist"` -> `funcs` 表项 `{name=0x448060,index=0x32,callback=0x40dd64}` 命中，`cgi_action[0x32]` / `*(obj.cgi_action + 0xc8)` 被置为 `1`
  - `body.hidd_coexist_flag` `缺失` -> `cgi_value("hidd_coexist_flag")` 在 `0x40de14` 返回 `NULL`，`*(0x10010000 - 0x2f80)` 即 `0x1000d080` 保持 `NULL`
- 执行顺序:
  1. 请求 `POST /apply.cgi?/shares` 进入 `do_apply -> cgi_setobject`
  2. `cgi_setobject` 读取 `submit_flag`，匹配 `wifi_channel_coexist`，设置 `cgi_action+0xc8 = 1` 并调用回调 `0x40dd64`
  3. 回调在 `0x40de14` 读取 `hidd_coexist_flag`，由于该字段缺失返回 `NULL`，所以 `0x1000d080` 不会被写入有效指针
  4. `cgi_commit` 在 `0x40e838/0x40e840` 根据 `cgi_action+0xc8` 调用 `cmd_wifi_coexist`，并在 delay slot 把 `a0 = *(0x1000d080)` 载入为 `NULL`
  5. `cmd_wifi_coexist` 在 `0x4124dc` 执行 `lb v0, (a0)`，触发 `SIGSEGV`

## 数据流细节

- 哪些数据包字段控制了哪些变量:
  - `body.submit_flag = "wifi_channel_coexist"` 只负责命中 `funcs` 表项并设置 `cgi_action[0x32]`，保证控制流到达 `cmd_wifi_coexist`
  - `body.hidd_coexist_flag` 才是 `cmd_wifi_coexist` 的实参来源；本样本中该字段缺失，导致返回值为 `NULL`
  - `body.wan_dhcp_gateway`、`body.wan_proto`、`body.wan_gateway`、`body.%20timestamp` 在当前崩溃路径上未看到进入 `cmd_wifi_coexist` 实参的数据流
- 哪个函数读取了source字段:
  - `sym.cgi_value@0x40cf10` 遍历请求参数键值对；在 `0x40de14` 被以 key `hidd_coexist_flag` 调用，未命中时返回 `0`
- 哪个函数写入 / 拼接 / 格式化了攻击者可控数据:
  - `0x40dd64` 是 `wifi_channel_coexist` 的配置回调；它在 `0x40de28` 只有当返回值非空时才会把结果写到 `0x1000d080`
  - 当前样本因为 `cgi_value("hidd_coexist_flag") == NULL`，所以这次写入没有发生，留下空指针
- 最终如何到达sink:
  - `cgi_setobject` 先因 `submit_flag` 把 `cgi_action+0xc8` 置 1
  - `cgi_commit` 看到 `cgi_action+0xc8 == 1`，在 `0x40e840` 把 `a0` 从 `0x1000d080` 取出
  - `cmd_wifi_coexist` 在 `0x4124dc` 直接解引用 `a0`，没有空指针检查，因此崩溃

## 误报检查

- 为什么这是一个真实漏洞，或者为什么它更像误报:
  - 崩溃信号、调用路径、参数来源和 fault 指令可以闭合成完整链条，不是只看现象下结论
  - 崩溃不是由 `wan_gateway` 的长字符串造成；当前实际 crash path 只依赖 `submit_flag` 和缺失的 `hidd_coexist_flag`
  - `cmd_wifi_coexist` 的第一条有效逻辑指令就是 `lb v0,(a0)`，而调用点明确把 `a0` 载为 `NULL`
- 当前缺失的证据:
  - 无关键缺失；虽然没有寄存器快照，但 trace + 调用点 + 反汇编已经足以确认 `a0` 为 `NULL`
- 对当前现象的替代解释:
  - 最合理的替代解释是“其他字段触发了别的内存破坏”，但现有 trace/反汇编不支持这一点，因为实际 fault 发生在独立的空指针解引用路径上
