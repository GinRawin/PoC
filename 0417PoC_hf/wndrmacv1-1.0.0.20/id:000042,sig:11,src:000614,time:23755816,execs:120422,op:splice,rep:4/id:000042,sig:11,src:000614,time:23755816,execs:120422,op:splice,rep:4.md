## 摘要

- 判定: `确认漏洞`
- Sink位置: `/usr/sbin/uhttpd` `0x439a2c` `0x439aac`
- Source位置: `/usr/sbin/uhttpd` `0x439a2c` `0x439a68`
- 漏洞二进制: `/usr/sbin/uhttpd`
- 漏洞类型: `NULL pointer dereference`
- 一句话根因: `qos_delmac` 处理函数先通过键查找 helper 读取 `select_qoslist_num`，字段缺失时返回 `NULL`，结果被保存到 `s2` 后在 `0x439aac` 直接执行 `lb v1, (s2)`，没有做空指针检查。
- 数据包字段 -> 变量赋值:
  - `body.submit_flag = "qos_delmac"` -> `0x40e0a8` 调用查找 helper 取回字符串，`0x40e0c0` 保存到 `s1`，随后在 `0x40e130` 遍历 handler 表并命中 `0x10000870 -> 0x439a2c`
  - `body.select_qoslist_num` `缺失` -> `0x439a68` 调用查找 helper，返回 `v0 = NULL`，`0x439a84` 保存为 `s2 = NULL`
  - `body.select_editnum_mac` `缺失` -> `0x439a88` 再次调用查找 helper 得到 `NULL`，随后 `0x439aa0` 调用 `0x40d188("qos_mac_list", NULL)`，函数在 `0x40d1d4` 走失败路径并返回 `-1`，该值不是崩溃实参
- 执行顺序:
  1. 请求以 `POST /apply.cgi?USB_browse.htm?openfile=USB_Folder_creat.htm` 进入 `uhttpd`，`0x40e0a8` 读取 `submit_flag`，得到 `qos_delmac`
  2. `0x40e130` 遍历 CGI handler 表，字符串 `qos_delmac` 命中表项 `0x10000870`，调用回调 `0x439a2c`
  3. `0x439a68` 读取 `select_qoslist_num` 得到 `NULL`，`0x439a88` 再读取 `select_editnum_mac`，`0x439aa0` 处理其返回值后继续执行，并在 `0x439aac` 对 `s2` 解引用触发 `SIGSEGV`

## 数据流细节

- 哪些数据包字段控制了哪些变量:

  - `body.select_qoslist_num` 控制 `0x40cf10` 的返回值；本样本中该字段缺失，因此 `v0 = NULL`，并在 `0x439a84` 赋给 `s2`
  - `body.select_editnum_mac` 只影响 `0x40d188` 的返回值；本样本中该字段同样缺失，所以函数直接返回失败值，未成为崩溃指针
  - `body.endis_wla_radio` 和 `body.%20timestamp` 在已观测到的崩溃路径上没有被消费
- 哪个函数读取了source字段:
  - `0x40cf10` 是键值查找 helper。其循环体在 `0x40cf4c-0x40cf74` 遍历 `{key, value}` 表项，匹配后返回 `4(s0)` 指向的 value 指针
  - 该 helper 在 `0x40e0a8` 被用于读取 `submit_flag`，在 `0x439a68` 被用于读取 `select_qoslist_num`，在 `0x439a88` 被用于读取 `select_editnum_mac`
- 哪个函数写入 / 拼接 / 格式化了攻击者可控数据:
  - `0x40cf10` 把匹配到的 value 指针放入 `v0`，随后 `0x439a84` 执行 `move s2, v0`
  - `0x40d188` 会在参数有效时用格式串 `"%s%d"` 组合出诸如 `qos_mac_list%d` 的键名，但本次 trace 只走到了 `0x40d1d4` 失败分支，没有把该结果传播到 sink
- 最终如何到达sink:
  - `submit_flag=qos_delmac` 使执行流进入 `0x439a2c`
  - `0x439a68` 以键 `"select_qoslist_num"` 调用 `0x40cf10`，由于请求体里没有该字段，返回 `NULL`
  - `0x439a84` 将该 `NULL` 赋给 `s2`
  - `0x439aac` 执行 `lb v1, (s2)`，对空指针地址 `0x0` 解引用，触发 `SIGSEGV`

## 误报检查

- 为什么这是一个真实漏洞，或者为什么它更像误报:
  - 崩溃地址明确落在 `uhttpd` 可执行段内，且 `trace/entry_trace.txt` 与 `trace/usr_sbin_uhttpd.txt` 都以 `0x439aa8 -> SIGSEGV` 结束
  - 反汇编表明 fault site 是真实的 `lb v1, (s2)`，`s2` 来自上一个 source 查找结果，不是模糊的“崩溃附近猜测”
  - 控制流选择器 `submit_flag=qos_delmac`、source 查找键 `select_qoslist_num`、sink 实参 `s2` 三者都能被同一条 trace 链解释
- 当前缺失的证据:
  - 没有符号表，因此 helper 的源码函数名只能以行为描述；但这不影响对 source、变量和 sink 的地址级确认
- 对当前现象的替代解释:
  - 最合理但已被排除的替代解释是“崩溃由超长 `endis_wla_radio` 覆写导致”。实际 trace 未进入任何处理该字段的路径，崩溃前最后一次危险读是对缺失字段返回的 `NULL` 做字节读取，因此该替代解释不成立
