# 漏洞分析: wndr37avv2-1.0.0.10 / id:000023,sig:11,src:000016,time:5664187,execs:22276,op:(null),pos:0

## 摘要

- 判定: `确认漏洞`
- Sink位置: `/usr/sbin/uhttpd sym.config_plc_dev_config@0x00439de0 -> sym.imp.atoi@0x0043afd0 (callsite 0x00439e3c)`
- Source位置: `/usr/sbin/uhttpd sym.config_plc_dev_config@0x00439de0 -> sym.cgi_value("plc_dev_select_num") callsite 0x00439e28 / NULL return at 0x004090cc`
- 漏洞二进制: `/usr/sbin/uhttpd`
- 漏洞类型: `NULL pointer dereference / remote DoS`
- 一句话根因: `submit_flag=plc_dev_config` 命中 `config_plc_dev_config` 后，代码无检查地对 `cgi_value("plc_dev_select_num")` 的返回值执行 `atoi`，而当前请求未提供该字段，导致 `atoi(NULL)` 崩溃。
- 数据包字段 -> 变量赋值:
  - `body.submit_flag = "plc_dev_config"` -> `cgi_setobject` 中 `s1`，用于匹配 `obj.funcs` 表并选择 `config_plc_dev_config`
  - `body.plc_dev_select_num` 缺失 -> `config_plc_dev_config` 中 `v0 = cgi_value(...)` 返回 `NULL`，随后 `move a0, v0` 传给 `atoi`
- 执行顺序:
  1. `POST /apply.cgi?` 请求进入 `cgi_setobject`，`cgi_value("submit_flag")` 取到 `plc_dev_config`
  2. `cgi_setobject` 遍历 `obj.funcs`，字符串比较命中后通过函数指针调用 `config_plc_dev_config`
  3. `config_plc_dev_config` 调用 `cgi_value("plc_dev_select_num")` 取参数，因字段缺失返回 `NULL`
  4. `config_plc_dev_config` 立刻执行 `atoi(NULL)`，trace 落到 `0x0043afd0` 并以 `SIGSEGV` 结束

## 数据流细节

- 哪些数据包字段控制了哪些变量:
  - `body.submit_flag` 控制 `cgi_setobject` 选择哪一个配置处理函数，是到达 sink 的关键控制字段。
  - `body.plc_dev_select_num` 本应提供给 `config_plc_dev_config`；本次它缺失，直接导致 `v0 == NULL`。
  - 其他字段如 `endis_wl_wmm`、`endis_wla_wmm`、`qos_endis_wmm`、`%20timestamp` 在已观测崩溃链中没有进入本次 sink。
- 哪个函数读取了source字段:
  - `sym.cgi_setobject@0x00416940` 通过 `cgi_value("submit_flag", ...)` 读取 `submit_flag`
  - `sym.config_plc_dev_config@0x00439e18` 通过 `cgi_value("plc_dev_select_num", ...)` 读取必填字段
- 哪个函数写入 / 拼接 / 格式化了攻击者可控数据:
  - 本次崩溃不是字符串内容污染到危险函数，而是 `cgi_value` 查找失败后返回空指针；危险实参由 `move a0, v0` 在 `0x00439e40` 直接构造。
- 最终如何到达sink:
  - `submit_flag` 命中 `plc_dev_config` 分支
  - `config_plc_dev_config` 在 `0x00439e28` 调用 `cgi_value("plc_dev_select_num")`
  - `cgi_value` 循环比较参数名，未命中时在 `0x004090cc` 返回 `0`
  - 返回值在 `0x00439e40` 被移动到 `a0`
  - `0x00439e3c` 调用 `atoi`，实际进入 `0x0043afd0` 后因 `a0 == NULL` 触发崩溃

## 误报检查

- 为什么这是一个真实漏洞，或者为什么它更像误报:
  - 这是一个真实漏洞。崩溃并非仿真噪声，也不是日志误判；入口 trace 明确显示控制流从 `cgi_setobject` 进入 `config_plc_dev_config`，最后落到 `atoi` 的导入桩并以 `SIGSEGV` 结束。根因是缺失参数未校验，不依赖未验证的外部假设。
- 当前缺失的证据:
  - 没有缺少判定所必需的关键证据。虽然没有运行时寄存器转储，但静态调用点、trace 顺序、请求内容与崩溃位置已经足够闭环。
- 对当前现象的替代解释:
  - 最合理的替代解释是 libc/导入桩异常，但这与 `cgi_value` 返回 `NULL`、紧接着调用 `atoi` 的代码路径相比明显更弱，且不能解释为什么仅在缺少 `plc_dev_select_num` 时命中该路径。
