# 漏洞分析: wndr37avv2-1.0.0.10 / id:000019,sig:11,src:000004,time:3194954,execs:12804,op:(null),pos:0

## 摘要

- 判定: `确认漏洞`
- Sink位置: `/usr/sbin/uhttpd fcn.0040ad34 0x40ade0 (jalr strcpy，delay slot 0x40ade4 将 a1=v0)`
- Source位置: `/usr/sbin/uhttpd fcn.0040ad34 0x40adcc (call cgi_value("DNSAssign", s3, s4))`
- 漏洞二进制: `/usr/sbin/uhttpd`
- 漏洞类型: `NULL 指针解引用 / 远程拒绝服务`
- 一句话根因: `pptp` 配置处理函数从请求参数中读取 `DNSAssign` 后未判空，直接把 `cgi_value()` 返回值作为 `strcpy` 的 `src`，当该字段缺失时以 `NULL` 调用 `strcpy` 并崩溃。
- 数据包字段 -> 变量赋值:
  - `body.submit_flag="pptp"` -> `cgi_setobject` 中 `s1=v0`，匹配函数表项 `"pptp" -> 0x40ad34`，把控制流送入 `pptp` handler
  - `body.DNSAssign` 缺失 -> `fcn.0040ad34` 中 `v0 = cgi_value("DNSAssign", s3, s4)` 返回 `NULL` -> `a1=v0` 作为 `strcpy` 的 `src`
- 执行顺序:
  1. 请求命中 `apply.cgi` 路径，trace 进入 `post_apply/do_apply -> cgi_setobject`
  2. `cgi_setobject` 读取 `submit_flag`，在 `obj.funcs` 中匹配到 `"pptp"`，调用 `0x40ad34`
  3. `0x40ad34` 读取 `DNSAssign` 失败得到 `NULL`，随后执行 `strcpy(sp+0x30, NULL)` 触发 `SIGSEGV`

## 数据流细节

- 哪些数据包字段控制了哪些变量:
  - `request.handler_name = "apply.cgi?/top.html timestamp="` 控制请求进入 `apply.cgi` 处理路径
  - `body.submit_flag = "pptp"` 控制 `cgi_setobject` 在函数表中选择 `pptp` 对应 handler `0x40ad34`
  - `body.DNSAssign` 才是危险实参来源；本样本里该字段缺失，导致 `cgi_value("DNSAssign", ...)` 返回 `NULL`
  - `body.wan_proto="pppoe"`、`body.http_passwd`、`body.%20timestamp` 在崩溃前未参与危险数据传播；其中 `check_timestamp` 在 `0x416860` 直接返回 `0`
- 哪个函数读取了source字段:
  - `fcn.0040ad34` 在 `0x40adcc` 调用 `cgi_value`
  - 调用前 `a0` 被装载为字符串 `0x43ceb4 -> "DNSAssign"`，`a1=s3`，`a2=s4`
- 哪个函数写入 / 拼接 / 格式化了攻击者可控数据:
  - `cgi_value` 在 `0x40909c/0x4090c4` 遍历 CGI 键值对并返回对应 value 指针；字段缺失时返回 `0`
  - `fcn.0040ad34` 在 `0x40ade0` 调用 `strcpy`，目的缓冲区为 `s2 = sp+0x30`，源参数在 delay slot `0x40ade4` 被设置为 `v0`
- 最终如何到达sink:
  - `submit_flag="pptp"` -> `cgi_setobject` 匹配函数表项 `"pptp" -> 0x40ad34`
  - `0x40adcc` 读取 `DNSAssign`
  - 因请求体中不存在 `DNSAssign`，`cgi_value` 返回 `NULL`
  - `0x40ade0/0x40ade4` 直接执行 `strcpy(sp+0x30, NULL)`，触发崩溃

## 误报检查

- 为什么这是一个真实漏洞，或者为什么它更像误报:
  - 这是一个真实漏洞。崩溃不是日志假象，而是 HTTP 请求处理路径中的真实 `SIGSEGV`；trace、函数表和反汇编共同证明 `submit_flag` 可把控制流带到 `pptp` handler，而缺失的 `DNSAssign` 会作为 `NULL` 进入 `strcpy`。
- 当前缺失的证据:
  - 没有影响结论的关键缺口。唯一未直接看到的是 libc 内部 `strcpy` 的首条 fault pc，但调用点参数已经足够确认 `src=NULL`。
- 对当前现象的替代解释:
  - 最接近的替代解释是 trace 只停在 `0x40add4` 而未展开到外部 `strcpy`，但这更像 trace 粒度限制；它不能解释 `cgi_value("DNSAssign")` 返回 `NULL` 后立刻准备调用 `strcpy` 这一事实。
