# 漏洞分析: wndr37avv2-1.0.0.10 / id:000016,sig:11,src:000100,time:1982529,execs:8665,op:(null),pos:0

## 摘要

- 判定: `确认漏洞`
- Sink位置: `/usr/sbin/uhttpd 0x40b4c4 0x40b56c`
- Source位置: `/usr/sbin/uhttpd 0x40b4c4 0x40b55c`
- 漏洞二进制: `/usr/sbin/uhttpd`
- 漏洞类型: `NULL pointer dereference` / 缺失 POST 参数校验导致的危险 `strcpy`
- 一句话根因: `submit_flag=ether` 命中 `ether` handler 后，代码先调用 `cgi_value("DNSAssign", ...)` 读取参数，再在没有判空的情况下直接执行 `strcpy(sp+0x20, v0)`；当请求体缺失 `DNSAssign` 时，`v0=NULL`，随后在 `strcpy` 中崩溃。
- 数据包字段 -> 变量赋值:
  - `request.handler_name=apply.cgi?...` -> 命中 `post_apply(0x406148)` 这条 apply CGI 解析路径
  - `body.submit_flag="ether"` -> `cgi_setobject(0x4168ec)` 中的 `s1`，并通过 `funcs["ether"]` 选择回调 `0x40b4c4`
  - `body.DNSAssign` 缺失 -> `cgi_value("DNSAssign", ...)` 返回 `v0=NULL`，随后在 `0x40b574` 被搬到 `a1`
  - `a1=NULL` -> `strcpy(sp+0x20, a1)` 的 source 实参
- 执行顺序:
  1. 请求以 `apply.cgi` 形式进入 `post_apply(0x406148)`，POST body 被拆成 CGI 键值对。
  2. `post_apply` 调用 `cgi_setobject(0x4168ec)`；该函数先读取 `submit_flag`，再在 `funcs` 表中匹配到 `"ether" -> 0x40b4c4`。
  3. `ether` handler 在 `0x40b55c` 调用 `cgi_value("DNSAssign", parsed_kv, count)`，由于包中没有该字段，返回 `NULL`。
  4. 同一 handler 紧接着在 `0x40b56c` 调用 `strcpy(sp+0x20, v0)`，`v0` 在 delay slot `0x40b574` 进入 `a1`，导致 `strcpy(NULL)` 并触发 `SIGSEGV`。

## 数据流细节

- 哪些数据包字段控制了哪些变量:
  - `request.handler_name` 中的 `apply.cgi` 让请求走到 `post_apply`，这是进入漏洞路径的入口条件。
  - `body.submit_flag="ether"` 在 `cgi_setobject` 中被读入 `s1`，并与全局 `funcs` 表逐项 `strcmp`，最终选中 `"ether" -> 0x40b4c4`。
  - `body.DNSAssign` 才是流向 sink 的 source 字段；本样本里它缺失，因此 `cgi_value("DNSAssign", ...)` 返回 `NULL`。
  - `body.hidden_pppoe2_policy` 与 `body.%20timestamp` 没有证据表明流入本次 sink；它们更像无关噪声。
- 哪个函数读取了source字段:
  - `uhttpd:0x40b55c` 调用 `cgi_value`，键名常量位于 `0x43ceb4`，内容为 `DNSAssign`。
- 哪个函数写入 / 拼接 / 格式化了攻击者可控数据:
  - `uhttpd:0x40b56c` 调用导入函数 `strcpy`，目标缓冲区为 `s2=sp+0x20`，源参数来自上一条 `cgi_value` 的返回值 `v0`。
- 最终如何到达sink:
  - `post_apply` 解析 body 后把键值数组传给 `cgi_setobject`。
  - `cgi_setobject` 先用 `submit_flag` 选中 `ether` handler。
  - `ether` handler 在 `0x40b55c` 读取 `DNSAssign`，返回值保存在 `v0`。
  - 随后的 `strcpy` 调用使用 `a0=s2`、`a1=v0`；由于 `v0=NULL`，真实 fault site 落在导入的 `strcpy` 内部，但其真实 sink 调用点是 `uhttpd` 的 `0x40b56c/0x40b574`。

## 误报检查

- 为什么这是一个真实漏洞，或者为什么它更像误报:
  - `container.console.log` 与 `entry_trace.txt` 都显示真实 `SIGSEGV`。
  - 反汇编能精确证明：`cgi_value("DNSAssign")` 的返回值未经任何判空，直接送入 `strcpy`。
  - `VulPacket.json` 中确实没有 `DNSAssign`，因此 `NULL` source 的成因能被当前样本自洽解释，不依赖猜测。
- 当前缺失的证据:
  - `entry_trace.txt` 没有记录到 libc 内部 `strcpy` 的具体 PC，只记录到回到 `uhttpd` 的块入口 `0x40b564` 后即发生 `SIGSEGV`。
  - 但这不影响结论，因为 `0x40b56c` 的 `strcpy` 调用点、`a1=v0` 的参数装载、以及 `v0` 来自 `cgi_value("DNSAssign")` 都已由反汇编固定。
- 对当前现象的替代解释:
  - 最合理的替代解释不是“误报”，而是“最后一个被 trace 到的 PC (`0x40b564`) 不是实际 fault instruction”；真实崩溃发生在随后导入的 `strcpy` 内部。这个解释与当前证据完全一致，并且仍然指向同一条真实漏洞链。
