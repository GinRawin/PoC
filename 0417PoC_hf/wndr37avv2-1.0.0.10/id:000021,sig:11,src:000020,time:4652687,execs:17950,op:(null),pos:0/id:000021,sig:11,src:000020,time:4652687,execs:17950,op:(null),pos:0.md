# 漏洞分析: wndr37avv2-1.0.0.10 / id:000021,sig:11,src:000020,time:4652687,execs:17950,op:(null),pos:0

## 摘要

- 判定: `确认漏洞`
- Sink位置: `/usr/sbin/uhttpd 0x412e60 0x412eb8 (jalr atoi), 崩溃落点 0x43afd0`
- Source位置: `/usr/sbin/uhttpd 0x412e60 0x412ea4 (cgi_value("select_del", ...))`
- 漏洞二进制: `/usr/sbin/uhttpd`
- 漏洞类型: `NULL` 指针解引用 / 参数校验缺失
- 一句话根因: `wlacl_del` 处理函数从请求中读取 `select_del`，未检查 `cgi_value()` 返回值是否为 `NULL`，就直接把结果作为 `atoi()` 的实参使用，导致崩溃。
- 数据包字段 -> 变量赋值:
  - `body.submit_flag = "wlacl_del"` -> `$17` 命中调度表中的 `wlacl_del` 项，进而调用处理函数 `0x412e60`
  - `body.select_del` 缺失 -> `cgi_value("select_del", ...)` 返回 `$v0 = NULL`
  - `NULL` -> `0x412eb0` 被移动到 `$a0` -> `0x412eb8` 调用 `atoi($a0)`
- 执行顺序:
  1. `POST /apply.cgi?/USB_browse.htm?openfile=USB_Folder_creat.htm` 携带 `submit_flag=wlacl_del` 进入 `uhttpd`
  2. `0x41693c` 读取 `submit_flag`，`0x4169d8` 用 `strcmp` 在提交处理表中匹配到 `wlacl_del`
  3. `0x416984` 取出该表项的函数指针并调用 `0x412e60`
  4. `0x412ea4` 调用 `cgi_value("select_del", ...)` 读取删除目标；当前请求缺失该字段，因此返回 `NULL`
  5. `0x412eb0` 把返回值放入 `$a0`，`0x412eb8` 直接调用 `atoi`
  6. trace 在 `0x43afd0`（`atoi` 的 PLT 跳板）后触发 `SIGSEGV`

## 数据流细节

- 哪些数据包字段控制了哪些变量:
  - `body.submit_flag` 控制调度分支，决定进入 `wlacl_del` 处理函数。
  - `body.select_del` 是该处理函数期望读取的删除索引；当前样本中该字段缺失，导致读取结果为 `NULL`。
  - `header.Host`、`body.%20timestamp` 在本条崩溃链中没有证据表明流入 sink；其中时间戳仅可能影响外围校验，不是本次空指针的直接来源。
- 哪个函数读取了source字段:
  - `0x412ea4` 调用 `cgi_value`，其第一个参数是常量字符串 `select_del`（由 `0x440000 - 0x27d0 = 0x43d830` 解析得到）。
- 哪个函数写入 / 拼接 / 格式化了攻击者可控数据:
  - 本次崩溃不依赖复杂拼接；关键是 `cgi_value("select_del", ...)` 的返回值直接进入寄存器 `$v0`，随后在 `0x412eb0` 被搬到 `$a0`。
  - 同一处理函数后续还会格式化 `wlacl%d` 并操作配置，但 trace 未执行到这些路径，说明崩溃发生更早。
- 最终如何到达sink:
  - `submit_flag=wlacl_del` -> `0x41693c` 读取 `submit_flag`
  - `0x4169d8` 遍历并 `strcmp` 命中 `wlacl_del`
  - `0x416984` 调用其 handler `0x412e60`
  - handler 在 `0x412ea4` 调用 `cgi_value("select_del", ...)`
  - 由于 `VulPacket.json` 中缺少 `select_del`，返回 `NULL`
  - `0x412eb0` `move $4, $2`，`0x412eb8` `jalr atoi`，导致崩溃

## 误报检查

- 为什么这是一个真实漏洞，或者为什么它更像误报:
  - 这是一个真实漏洞。崩溃并非仅靠日志猜测，而是能从 trace 和反汇编恢复出完整控制流: `submit_flag` 命中 `wlacl_del` handler，handler 读取缺失的 `select_del`，随后无判空调用 `atoi`。
  - `0x43afd0` 只是 `atoi` 的 PLT 跳板，不应被机械视为根因；真正的危险 sink 是 `0x412eb8` 处把未校验返回值送入 `atoi`。
- 当前缺失的证据:
  - 没有运行时寄存器转储来直接打印 `$a0 = NULL`，但 `VulPacket.json` 缺失 `select_del`，且 `0x412ea4` 与 `0x412eb8` 之间不存在任何非空修正分支，证据已足够支撑结论。
- 对当前现象的替代解释:
  - 最合理的替代解释是首次进入 `atoi` 的 PLT/Lazy binding 过程异常；但即便如此，也不能否定根因，因为该路径之所以到达 `atoi`，仍然是由于 `select_del` 缺失后未做空指针检查。换言之，输入触发的危险调用是确定的。
