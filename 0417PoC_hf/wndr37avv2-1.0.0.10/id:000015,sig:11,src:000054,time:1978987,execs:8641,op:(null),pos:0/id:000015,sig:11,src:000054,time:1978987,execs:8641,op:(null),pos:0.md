# 漏洞分析: wndr37avv2-1.0.0.10 / id:000015,sig:11,src:000054,time:1978987,execs:8641,op:(null),pos:0

## 摘要

- 判定: `确认漏洞`
- Sink位置: `/usr/sbin/uhttpd 0x41268c 0x412718 (jalr strcmp)`
- Source位置: `/usr/sbin/uhttpd 0x409060 0x4090cc (cgi_value("wl_enable_router", ...) 未命中后返回 NULL)`
- 漏洞二进制: `/usr/sbin/uhttpd`
- 漏洞类型: `NULL pointer dereference / DoS`
- 一句话根因: `submit_flag=wlan_adv` 命中 `uhttpd` 的 `0x41268c` 处理函数后，代码直接把 `cgi_value("wl_enable_router", ...)` 的返回值传给 `strcmp`，未检查该字段缺失时返回的 `NULL`。
- 数据包字段 -> 变量赋值:
  - `body.submit_flag = "wlan_adv"` -> `cgi_setobject(0x4168ec)` 中 `s1 = cgi_value("submit_flag", ...)`，随后在 `obj.funcs` 表中匹配到表项 `(0x43c998 "wlan_adv", 0x0000000c, 0x41268c)` 并调用 `0x41268c`
  - `body.wl_enable_router` 缺失 -> `cgi_value("wl_enable_router", ...)` 返回 `v0 = NULL` -> `s3 = v0` -> `a0 = s3` 传入 `strcmp`
  - `body.wla_enable_router` 缺失 -> 第二次 `cgi_value("wla_enable_router", ...)` 也会返回 `NULL` 并写入 `s5`，但在到达该后续逻辑前已先因 `s3` 触发崩溃
- 执行顺序:
  1. `POST /apply.cgi?` 请求进入 `uhttpd`，`cgi_setobject(0x4168ec)` 先通过 `cgi_value("submit_flag", ...)` 取到 `submit_flag=wlan_adv`
  2. `cgi_setobject` 在分发表中将 `"wlan_adv"` 映射到处理函数 `0x41268c`
  3. `0x41268c` 调用 `cgi_value("wl_enable_router", ...)`，trace 显示其走到 `0x4090cc` 返回 `NULL`
  4. 返回后执行 `s3 = v0`，随后在 `0x412718` 调用 `strcmp(s3, "1")`
  5. 因 `s3 == NULL`，程序在 `strcmp` 内部对空指针解引用，`entry_trace` 以 `SIGSEGV si_addr=NULL` 结束

## 误报检查

- 为什么这是一个真实漏洞，或者为什么它更像误报:
  - 崩溃在 `container.console.log` 和 `trace/entry_trace.txt` 中都明确出现，且 `si_addr=NULL` 与 `strcmp` 空指针实参完全一致
  - 同一个请求对象里，`cgi_value("submit_flag", ...)` 成功返回并完成分发，说明不是通用解析失败；真正出错的是 handler 对缺失字段 `wl_enable_router` 未做空指针校验
  - 分发表中存在明确表项 `("wlan_adv", 0x0000000c, 0x41268c)`，控制流可以从数据包字段精确落到崩溃 handler
- 当前缺失的证据:
  - 无关键缺失证据；即使没有继续跟进到 libc `strcmp` 内部指令，`0x412718` 的调用点、`a0=s3=NULL` 的寄存器装载关系和 `si_addr=NULL` 已足够闭合链条
- 对当前现象的替代解释:
  - 替代解释是“请求解析器整体失效导致所有 `cgi_value` 都返回 `NULL`”，但这与 `submit_flag` 查找成功、dispatch 成功跳入 `0x41268c` 的 trace 事实矛盾，因此不成立
